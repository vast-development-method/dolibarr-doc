# Operational evidence for installation-only and gated records

Which records must a replacement implementation maintain when a user posts an entry, reconciles a statement or signs a document? This register follows 23 physical definitions from the [installation boundary register](installation-boundaries.md) to the operations that could plausibly use them. Release 24.0.3 contains one confirmed logging path behind separately enabled features and one explicitly deprecated state table. For the other 21 definitions the traced core workflows provide no evidence of an operational reader or writer of the named table. An external integration can have a different storage contract.

## How these records enter the database

The initial installer loads ordinary table definitions and then their key files. In both passes it skips filenames containing a hyphen. Accounting, banking, recruitment, surveys and assisted authoring each load their own suffixed definitions during module activation. Thus activating a stable module can install a table even if none of that module's ordinary operations populate it. Source locations in the tables below use the repository root. Declaration filenames in the boundary register resolve under `htdocs/install/mysql/tables/`.

| Installation route | Release location |
| --- | --- |
| Core tables, then core keys | `htdocs/install/step2.php:190-218,288-317` |
| Accounting and banking table families | `htdocs/core/modules/modAccounting.class.php:418-428`, `htdocs/core/modules/modBanque.class.php:257-266` |
| Recruitment and survey table families | `htdocs/core/modules/modRecruitment.class.php:390-399`, `htdocs/core/modules/modOpenSurvey.class.php:179-189` |
| Assisted authoring table family | `htdocs/core/modules/modAi.class.php:373-384` |

## Separately gated request logging

**`ai_request_log` has confirmed readers and writers.** Module activation loads its schema. The normal setup tabs expose assistant and tool-server configuration only at feature level 2 or higher. Each caller separately checks its own enablement setting, and the shared writer returns immediately unless request logging is enabled. The administrative viewer checks administrator access and module enablement. The ordinary assisted-authoring feature does not by itself establish that requests are logged. See `htdocs/ai/lib/ai.lib.php:319-339,426-444`, `htdocs/ai/assistant/parse_intent.php:51-65,512-546`, `htdocs/ai/server/mcp_server.php:55-62,177-185,209-220`, `htdocs/ai/admin/log_viewer.php:85-95`.

Each call to the writer attempts one insert for the current entity and user. It records the query, tool, provider, elapsed time, confidence, outcome, error and raw request/response. Raw input and output longer than 60,000 characters are shortened and marked. Optional agenda and hash columns exist in the declaration, but this writer does not populate them. The viewer queries entities within scope and supports deletion. The bundled purge command uses a positive retention period to delete older records. This evidence establishes a diagnostic storage contract for the gated paths, without adding that capability to the stable ERP business workflow. See `htdocs/install/mysql/tables/llx_ai_request_log-ai.sql:21-40`, `htdocs/ai/lib/ai.lib.php:323-362`, `htdocs/ai/admin/log_viewer.php:100-130,187-195,224-240`, `scripts/ai/purge_logs.php:55-78`.
