# Commercial decisions and document output

A sales manager may sign several offers, classify fulfilled orders or close actual shipments from a list. An offer signature records a sales decision. Closing the order records completion in the order register. Closing the physical shipment can post inventory under a different policy. A generated PDF supplies another kind of evidence. Each operation has a distinct transaction boundary.

## State decisions

| Selection and instruction | Decision and effect | Mixed batch behavior |
| --- | --- | --- |
| Offers, validate | Each fetched offer must be draft. The offer's validation operation issues it. | The list accumulates failures and rolls back the whole selection on error. Early per-record notices can precede the eventual rollback. |
| Offers, sign or reject | Sign takes a validated offer to signed. Rejection normally takes a validated offer to rejected and also admits a draft under the skip-accept/refuse policy. The actor calls the closing operation directly. | Failure to fetch, ineligible state or a failed transition records an error. The outer transaction covers every selected offer. A recorded signature here is an internal status decision. |
| Offers, classify billed | The class condition transfers a signed offer to billed and records closure time and actor. The list treats a zero result or error as failure. | An already ineligible offer can undo another selected offer's pending classification. This instruction creates no invoice lines. |
| Customer orders, validate | A fetched draft is issued with its stored warehouse ID or zero. The class can require a warehouse if stock posts at this point. | A non-draft, failed load or unsuccessful validation records an error for the whole set. |
| Customer orders, classify shipped | Select validated, shipment-in-process or already closed orders. The close operation stores closure actor and date and emits the order-close event. Already closed returns zero and is accepted by this list. | An ineligible order or failed transition rolls back the selection. The instruction itself adds no physical shipment rows, lots or stock allocations. |
| Customer orders, classify billed | Sets the independent billed flag for qualifying non-drafts. The class returns zero immediately for an order already marked billed. | The list treats zero as failure and rolls back on the first failed result or fetch. A previously billed row matters on retry. |
| Customer orders, cancel | The action admits validated orders only, invokes cancellation and stops on ineligible status or a negative result. | One database transaction includes the selection. An order fetch returning non-positive inside this cancellation loop is skipped. |
| Supplier orders, validate | For selected drafts, call validation. If direct approval is enabled, the operator has authority and the warehouse-sensitive stock condition allows it, the action also calls approval. | The outer transaction covers the selection. Non-drafts are skipped in this handler. Validation failure raises the transaction error. The auto-approve branch announces approval without checking that call's returned result. The persisted state distinguishes validation from final approval. |
| Shipments, close | Each fetched shipment is passed to its own close routine. That routine owns eligibility, source-order effects and any closure-time stock posting. | The list accumulates negative closure results and continues. It has no surrounding transaction across shipments. One completed shipment can remain closed when another fails. |

See [stock posting decisions](../policies/stock-posting-decisions.md) for the physical movements triggered by a chosen transition.

Consider an operator signing three offers. The first two are validated and the third is still a draft. The sign action reports the third as ineligible and rolls back both earlier status changes. Classifying two actual shipments closed works differently. If the first closure succeeds and the second cannot post its lot movement, the first can stay closed. On retry, inspect the durable state of both source records.

## Issue and delete invoices

Customer and supplier invoice lists share a bulk validator. Its entry requires the list's creation/write grant. With stock enabled, posting inventory on customer invoice issue disables the common customer bulk validation route. The equivalent supplier-invoice option disables the supplier route. A separate workflow that creates and issues from source documents must be traced at its own entry point. When chronological issuance is configured for customer invoices, the validator orders selected IDs by invoice date before issuing them. Ties have no additional ordering key in this query.

The default validator opens one transaction for the full selection and stops at the first failed fetch, zero result or negative validation. A setting keyed by record class can instead commit each successful issue before moving to the next. The failure still stops the loop. For three drafts A, B and C in that processing order, if B fails, the default path rolls back A and B and leaves C unattempted. The per-record path retains A, rolls back B and leaves C unattempted. A document regeneration error after successful issue reports the file problem without treating the business validation as failed. The class can also apply its own date, line and permission rules. [Issue admission](../policies/form-defaults-and-invoice-admission.md)

Deletion deduplicates the selection. The common operation skips issued customer invoices and objects with a failing erasability predicate, recording associations or ineligibility for the operator. A zero result from the delete operation can become a warning. A negative delete result or failed fetch is a hard failure and rolls back the attempted set. This distinction permits a deletable draft and an ineligible issued invoice to yield one deletion, yet a later database failure can undo that draft deletion. The supplier invoice list offers general deletion under supplier delete authority and delegates its record-specific constraints.

## Produce a new document or combine existing files

Regeneration loads each selected record and uses that record's stored model. In a multilingual company the output language is resolved per record. An explicitly selected language takes precedence. Otherwise the operation attempts the party or record's language, fetching the party where necessary. Each iteration resets the working language and party reference so the last customer's translation is not carried over. Visibility of reference, description and detail follows the active rendering settings. A failed fetch or generator return stops the loop. Its database transaction cannot recall a file already written to storage.

The combine command identifies successfully fetched records and their public references. Its ordinary search matches the reference PDF or a suffixed document-model filename, enumerates candidates newest first, and for each reference chooses the first candidate containing it. The final choice uses substring matching within that candidate set, which matters for references such as INV-1 and INV-10. A reference with no matching file contributes no pages. The selected PDFs are concatenated to a separately named, timestamped output. Merging preserves the printed language, dates and totals in the existing files. A change to an invoice or to its customer's language reaches a new combined output only if the constituent documents reflect it.

The mailing path has its own send confirmation, contact resolution, transport and activity history. Changing options on the preparatory form does not send. See [commercial message delivery](../specification/administration/commercial-message-delivery.md).
