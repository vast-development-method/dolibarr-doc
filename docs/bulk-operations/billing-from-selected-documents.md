# Billing from selected orders, shipments and receipts

Four lists create invoices from selected documents. The starting list determines whether the quantity is the whole order or the quantity physically handled. All four routes offer one invoice per source or reuse of one invoice per party. Reuse lasts only for that invocation. It does not search for and append to a draft made on a previous run.

## Admission and invoice identity

| Source selected | Admission in this conversion loop | Origin and grouping |
| --- | --- | --- |
| Customer order | Unreadable or missing orders are skipped when fetch returns non-positive. Draft, cancelled and already-billed orders are skipped with a warning when fetched. Other eligible orders can still produce invoices. | The first order for each customer supplies the standard invoice, payment terms and method with party fallback, project, custom header values and, when enabled, document currency. An ungrouped invoice also receives the customer's order reference. |
| Shipment | The loop skips a non-positive shipment fetch. It does not repeat the order route's status/billed exclusion. Quantity comes from the shipment contents. | Uses the source order's terms and payment method with party fallback, the shipment project and custom header values. Currency falls back from order to customer to shipment. The invoice receives a link to each shipment used. |
| Supplier order | The loop skips a non-positive order fetch, then allocates its invoice. It has no corresponding test for approved status or an earlier bill in this loop. | Standard payable takes supplier, VAT reverse-charge preference, order payment terms/method, project and currency. The vendor reference is the order's supplier reference, or an incrementing value seeded from the current timestamp. Each order has a source link. |
| Receipt | Input IDs are sorted. A missing or draft receipt records an error, which can roll back the entire selection. A closed or validated receipt can pass this test. | Payment terms, method, bank account, transport and currency are filled field by field from receipt, then its origin, then the supplier when available. One receipt supplies its reference. Grouping creates a reference from receipt label, timestamp and supplier ID. The invoice keeps receipt and supplier-order links. |

A grouped invoice uses the first created header for that party. A difference in project, payment terms, discount basis or source currency does not automatically start a second group. For receipts the code compares the origin currency to the invoice currency and appends an error description on mismatch. That comparison does not increment the transaction error counter; by itself it cannot guarantee rejection. A grouped extract or rebuild must retain the source IDs and currencies to explain such a transaction. Currency conversion and rounding still depend on the receiving invoice operation. It would be incorrect to infer that every original rate and document-currency amount is preserved on every route.

## How the lines are derived

**Customer orders.** Ordinary lines carry the order's net unit selling price, ordered quantity, VAT, both local taxes, line discount, stock item or service, cost information, unit and source line ID. The routine takes the most specific populated start and end dates in the order planned date, actual date and explicit line date. Parent/child grouping is reconstructed around special product-type lines. Grouped rows include the originating order reference and date in the description. The writer assigns a running sequence by party. The optional shipment-link policy adds related shipment links to an invoice made from an order; copying links alone does not change the quantity from ordered to shipped. Negative unit-price rows normally become absolute discounts for the customer, with the source net, VAT and gross magnitudes and rate. A company policy can leave negative rows in their original representation. [Sales conversion and partial billing](../specification/commercial/sales-conversion-and-partial-billing.md)

**Shipments.** When fetching an order-based shipment, the reader accumulates dispatched quantities belonging to the same origin line and retains the warehouse splits and batch detail. The quantity passed into the billing line is that accumulated shipped quantity. For positive lines the commercial price, discount and tax data come from the source document. Grouped descriptions identify the order and shipment and can include the shipping date. Each produced ordinary line carries a shipment-line origin. A selected shipment can link to other source documents. The transfer routine skips existing invoice links, compares overlapping source identifiers when grouped, and takes the first ID of each remaining source type. This operation should not be described as copying every relationship attached to every shipment.

**Supplier orders.** Ordinary payable lines use the order quantity, net unit price, rate, local taxes, discount, service dates, vendor product reference and unit. When copying a keyed supplier line, the conversion passes that line's owning order ID in the origin argument and its base purchase cost in the document-currency unit-price argument. This particular mapping differs from a receipt conversion, which supplies its loaded document-currency unit price. A negative unit price takes a separate absolute-discount route. Grouped lines append the source purchase-order reference. The order reference is also accumulated in the invoice's public note up to the configured reference limit.

**Receipts.** The reader starts with each receipt allocation, including separate lot or warehouse rows. It loads ordered quantity, rate, price, foreign unit price, VAT, discounts, descriptions and service dates from the associated supplier order line. On the positive-price route the invoice line receives the allocated quantity, its loaded pricing fields, and the supplier product reference. The conversion attempts to link the receipt to the payable line before checking the line writer’s result. It ignores the link writer’s return, so a stored line can lack this link. On the negative-price discount route, the amounts selected for the discount are the net, VAT and gross totals loaded from the supplier order line. These totals can span more than the partial allocation. A rebuild that models every discount as allocated quantity times unit price would miss this distinction. Closing or posting the payable and setting the receipt's billed status are also separate operations.

## Creation, issue and retry

Each conversion starts a database transaction around the selection. A checked failure in header or line creation rolls back the selection when the nested calls have closed their own transaction levels. Skipping an ineligible customer order raises a warning and processing continues. With automatic issue enabled, the customer-order, shipment and receipt paths stop at the first nonpositive validation result and request rollback. If supplier-invoice validation returns early on a stock error with a transaction level still open, the receipt caller’s rollback only reduces the nesting depth. The database transaction remains open.

Supplier-order billing calls validation but tests the earlier line or discount result. A positive earlier result can leave a draft committed after an early validation refusal. It can also commit an issued header after a subscriber error if validation changed the header before the subscriber ran. Read the header, permanent reference and relevant effects using a fresh connection before retrying. [Failure boundaries for each register](../conversion-recovery/selected-documents.md)

A source order can remain unclassified after a draft invoice was created. Invoice creation, classification by a workflow subscriber, issue, document-file generation and customer payment are separate events. Source links give evidence of invoices already created if the operator lost the response. Repeating the entire selection may create further drafts. Filesystem output and an external subscriber can have a different rollback boundary from database mutations. Read the [commercial workflow subscribers](../events/commercial-automation.md) for classification policies.

## Worked selections

A customer orders ten units at 20, with a 10% line discount and 15% VAT. Four units have shipped. Billing the full order produces 180.00 net and 27.00 VAT. Billing the four-unit shipment produces 72.00 net and 10.80 VAT. Both invoices can legitimately refer back to the order. Issuing both for the same sale without an intended staged-billing arrangement leaves 14 units billed against ten ordered. Shipment links alone cannot establish how much remains available for billing.

A purchasing clerk selects two validated receipts from one supplier for the same order line. One receipt records three units and the second five, at 12.50 net with no discount. A grouped payable has two source quantities, 37.50 and 62.50 net, totaling 100.00. A third, draft receipt in the same selection records an error and prevents the batch's ordinary database commit. By contrast, a draft customer order alongside two eligible customer orders is skipped while the two eligible orders can yield invoices. The operator needs the per-source result to distinguish a successful partial selection from a rolled-back conversion.
