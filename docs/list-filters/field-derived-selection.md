# How field declarations become register filters

An operator can display a field without being able to filter on it. Conversely, some registers accept a field search even when that field is hidden from the current column layout. To reproduce a result, start with the [register](screen-index.csv), resolve its [field-derived selectors](metadata-keys.csv), then apply its access scope, query conditions and relationships. The [literal request index](request-keys.csv) identifies inputs read explicitly by each register.

## Which registers read field names dynamically?

The 56-register inventory contains **163 declared register/field pairs across ten registers** whose input readers build names from nonempty field definitions. A pair counts once regardless of the number of date components, user layouts or modules enabled. The CSV gives the header table, stored field, label key, direct comparison, declared list visibility, effect of the input, date-range handling and overlap with a literal input on the same screen. All 163 fields have a corresponding column in the [relational model](../relational-model/README.md).

| Register | Header table | Fields | How the result is selected |
| --- | --- | ---: | --- |
| Bookkeeping templates | `accounting_transaction_template` | 9 | Reads the header fields. A user reference uses the numeric comparison mode. A single creator ID works. The chooser does not change the comparison into an ID-set match. With multi-company support disabled, the constructor removes the entity field before search inputs are read. |
| Fixed assets | `asset` | 32 | Reads header fields including acquisition and disposal amounts, dates, depreciation indicators and the asset model. Numeric fields support comparisons. Linked IDs and enumerated choices use integer sets. An encoded zero qualifies when it is a declared choice. The entity selector requires the field to survive multi-company setup. |
| Fixed asset models | `asset_model` | 13 | Reads model headers. The generic reader has a company-country default for a field named `fk_pays`. That field is absent from the model declaration, so this branch supplies no country filter in the standard register. |
| Intra-community reporting | `intracommreport` | 9 | Development feature. Declaration and export type are character columns with text codes, but the generic choice branch applies an integer-set comparison. For example, the value `deb` reduces to an integer set containing zero. That comparison cannot reliably distinguish the declared text choices. The reference also has an independently named input. |
| Inventory sessions | `inventory` | 16 | Reads the count header, including optional value date and selected warehouse or product. A matching line in a count for all products does not give its header a selected product. Category context, visibility and field availability are described in the [warehouse register guide](catalog-and-fulfillment.md). |
| Warehouse directory | `entrepot` | 18 | Maps the request `search_status` to the stored `statut`. Explicitly skips the submitted entity field and scopes the query to permitted stock entities. Physical quantity and value aggregates are displayed separately. |
| Internal ticket queue | `ticket` | 33 | Handles status groups, type codes and four positive linked-ID selectors separately. Other submitted header fields use their numeric or text comparison. Project and contract each have both a dynamically read name and a separate literal condition. The [ticket filter guide](people-and-services.md) gives the status expansion and named date bounds. |
| Product variant attribute definitions | `product_attribute` | 5 | Reads the row ID, internal reference, external reference, label and position. Number of option values and number of products are two separately named inputs. They qualify the grouped result after the detail joins. Neither count belongs to the five header declarations. |
| Salaries | `salary` | 23 | Reads header field names into a search collection, then builds predicates from separate named inputs. Three names overlap. `search_ref` compares the salary row ID, `search_label` compares the label and `search_amount` compares the numeric amount. A bare `search_fk_user` has no header-field predicate. The employee search operates on the joined user's login, surname, first name or email. |
| Users | `user` | 5 | Reads row ID, surname, first name, employee reference and national registration number. The query uses separate inputs for row ID and the two name fields. The two personnel identifiers can be displayed with the applicable HR permission and column selection. Entering their constructed field names adds no predicate. The general text search uses its own field set. |

Of the 163 pairs, **135** belong to the first eight registers. One of those is the explicitly skipped warehouse entity. Two are entity fields removed when multi-company support is off. The other **28** pairs belong to Salaries and Users. Six of their names affect the query through a separate literal input and 22 add no field-specific condition. Across all ten registers **11** constructed names also occur in the literal index. Use the pair of register and selector as the join key. Summing the row counts of the two indexes would count those 11 names twice.

The Donations register also loops over its object's fields. The standard donation object inherits an empty field declaration and adds no fields to it. Its explicit reference, donor, date and amount filters still apply. The other 45 registers do not read a submitted base-record name through a nonempty object-field loop. Some use definitions to populate column lists, format values, clear a form or choose general-text search fields. For example, the user-group register uses the group definitions during filter reset. The email-campaign and miscellaneous-payment registers contain no active generic base-field reader. Their explicit controls and optional attributes have their own rules.

## Visibility, dates and effective predicates

The declared visibility is a field property. In the generic column chooser, zero hides a column and a negative value normally starts it unselected. Different screens also apply module settings, field categories, personal column choices and grants. A constructor can remove a disabled field or hide a technical ID. The CSV records the declaration before those decisions. A hidden ID and an absent field have different effects. An ID still present in the object can be read by the generic search loop. A field removed before the loop has no constructed input. On Salaries the visibility of the external reference also follows the company setting.

| Date path | Behaviour |
| --- | --- |
| Bookkeeping templates, fixed assets, asset models, inventory sessions and the development trade report | Seventeen declared date fields support inclusive generated bounds. Append `_dtstartday`, `_dtstartmonth`, `_dtstartyear` or the corresponding `_dtend` components to the field selector. The lower bound starts at midnight and the upper bound ends at 23:59:59. The target is the underlying header field. A bare field input takes its normal direct comparison. |
| Warehouse directory | Both date fields can expose range widgets. The register reads the bare field names and never assembles these six components into bounds. Selecting a displayed date range alone leaves the query unchanged. |
| Internal ticket queue | Six date fields receive generic component names in the reader. The generic predicate loop does not turn those suffixed names back into the physical field. The three working named ranges use separate inputs for creation, first read and closure. |
| Salaries | Six dates have component-reading logic. The search collection does not supply conditions to the query. The working period-start and period-end controls use their separately named inputs. |

For example, an asset may be acquired in March and begin depreciation in April. A complete March `search_date_acquisition_dtstart` and `search_date_acquisition_dtend` range includes the asset. Using the same boundaries for `search_date_start` excludes it. On the warehouse register, entering the analogous generated boundaries for the last-modified field supplies no effective range. The visible label “From” does not establish which record or date the query will use.

## Names defined by configuration and relationships

- **Contact networks.** When social networking is enabled, the contact register creates one `search_` name per active network code. It matches the encoded value under that code in the contact’s stored network map. Back ends with the register’s regular-expression branch allow a match within the value. The fallback matches a prefix of that value. If the network is inactive, its input supplies no condition. An active code is installation data, outside the fixed field count.
- **Category selectors.** The bank account selection uses `search_category_bank_account_list`, warehouses use `search_category_warehouse_list`, and projects use `search_category_project_list` and `search_category_user_list`. These target category relationships. A creator’s category selects related projects by that creator. It does not assign a category to the project itself. Screen-specific operator and eligibility rules still apply.
- **Custom fields.** Where a register includes the shared optional-field reader and query handler, the ordinary prefix is `search_options_` followed by the configured field key. The queried optional record joins to its owning object. A date range may have either endpoint or both. A false Boolean includes a stored zero or null, while an unselected Boolean contributes no condition. Numeric fields, linked records, choice codes and multivalue fields use different comparison rules. A site's custom-field definitions and the register's effective object and join determine the actual search vocabulary.
- **Navigation and edits.** The customer invoice list reconstructs the components of its creation and modification date controls when preserving a search across pages. These repeat the existing filter state. In the three accounting assignment queues a name constructed from a line identifier supplies a proposed account to a write operation. That value changes an assignment when the operation succeeds and is outside the search-field count.

For a reproducible register test, keep the company, actor, feature settings, records and selected columns fixed. Record both the submitted key and the qualifying header IDs. On the user register, place distinct employee references on two visible users and give them different surnames. A direct surname search narrows the result. Submitting the same user's employee reference through the constructed field name alone leaves both eligible users in the result.
