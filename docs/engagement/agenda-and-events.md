# Agenda, resource reservations and event registration

A calendar event can organize internal work, record a customer interaction or represent a conference session. A conference registration adds a ticket holder and, for a paid event, a customer invoice. These records have different owners and lifecycle fields. Event Organization (2450) depends on Projects, Categories and Agenda (2400). Resources (63000) has its own activation and permissions. ## Calendar and resource rules

An agenda event identifies an event type, label, owner, entity and start date. It can link a project, task, third party or originating business record. Its assigned users and contacts carry their own participation attributes (mandatory, answer, and transparency). Creation requires an owner value, with zero explicitly permitted for anonymous events, and a resolvable event type. A missing assignment list falls back to the owner. Duplicate users are coalesced in the assignment insert loop. The event, assignments and creation trigger share a transaction. If a supplied end precedes the start, the creation method brings the end up to the start. Completion uses the percentage field, with −1 meaning inapplicable, 0 to do, 1–99 in progress and 100 complete. [Event creation](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/comm/action/class/actioncomm.class.php#L500-L601) · [Assignments and commit](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/comm/action/class/actioncomm.class.php#L697-L787) · [Completion labels](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/comm/action/class/actioncomm.class.php#L1648-L1693) · [Agenda guide](https://wiki.dolibarr.org/index.php/Module_Agenda)

The agenda REST read operation requires permission to read one's own events and resource access. Reading another owner's event also requires all-events read. Creating for someone else likewise requires the all-events creation right in addition to one's own creation right. The resource-assignment screen uses `resource.write` to add/update a resource link and `resource.delete` to remove it. [Agenda read](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/comm/action/class/api_agendaevents.class.php#L75-L96) · [Agenda create](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/comm/action/class/api_agendaevents.class.php#L240-L277) · [Assignment permissions](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/resource/element_resource.php#L110-L144)

| Decision | Stable behavior |
| --- | --- |
| Link a person or a physical resource | People assigned to the agenda event are stored as typed participant links. A resource booking connects the event to a particular resource and stores **busy** and **mandatory** separately. |
| Declare a resource busy | On the resource link form, with `RESOURCE_USED_IN_EVENT_CHECK` enabled, a busy physical-resource booking checks other busy bookings for the same resource on agenda events. Adding an overlapping booking raises an error. Updating a link checks for conflicts while excluding the current event. |
| Evaluate time boundaries | For ordinary bounded bookings, touching endpoints count as an overlap. For a new full-day event without an end, the code constructs local day boundaries. Availability on this screen is a pre-write query, so the evidence establishes a form-level check. |
| Show a conference or booth on the agenda | The session uses an agenda record and a separate event-organization status. Draft (0), suggested (1), not qualified (3) and canceled (9) map to progress −1. Confirmed (2) maps to 0 and done (4) maps to 100 on create/update. |

## Event registration to payment

| Owner | Records and relationships |
| --- | --- |
| Event project | Event-use flag, event dates, location, maximum attendees and registration price. A public registration can be for the event as a whole or a specific agenda conference. |
| Attendee | Registration reference, names and email, project/session, optional third party and invoice, subscription date, received amount and status. Draft (0), validated (1), used/showed up (5) and canceled (9). A used ticket represents attendance. |
| Billing | A paid registration links to one customer invoice through the attendee's invoice ID. Billable party and attendee can have different invoice-contact details. The payment references that invoice and can post to the configured provider bank account. |

[Event project fields](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/install/mysql/tables/llx_projet.sql) · [Ticket storage](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/install/mysql/tables/llx_eventorganization_conferenceorboothattendee.sql) · [Ticket states](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/eventorganization/class/conferenceorboothattendee.class.php#L54-L59)

1. The public form accepts the qualifying confirmed conference or validated event project. It requires a valid attendee email and country and, when a fee is due, a billing name/company. Existing registration lookup uses email plus project for a whole event or email plus agenda session for a conference. Previously registered unpaid attendees can update details. A previously recorded payment takes the attendee to an acknowledgement. [Public registration and lookup](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/eventorganization/attendee_new.php#L260-L342) · [Paid registration handling](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/eventorganization/attendee_new.php#L385-L403)
2. For a free event, the registration code can proceed without creating a paying third party. It sets the attendee status to validated before committing. For a fee-bearing event, it resolves or creates a billing third party. It creates or reuses a draft invoice linked by the attendee's invoice ID. If the invoice has no lines, it adds one service line at the project's **tax-inclusive** fee, quantity one, with the event date range. It commits the registration and draft invoice before redirecting the payer. [Third-party resolution](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/eventorganization/attendee_new.php#L490-L569) · [Invoice and free registration branches](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/eventorganization/attendee_new.php#L580-L684)
3. The successful attendee payment handler resolves the invoice, validates it, and allocates the provider amount to it. When banking is active it requires a configured bank account and requests a corresponding bank movement. On success it validates the attendee and writes the amount/date on the registration. The provider payment and local posting are separate events. The branch reports an error for a different settlement currency, and a missing bank mapping can leave a confirmed provider collection requiring reconciliation. Invoice validation occurs before the inner local payment transaction. [Payment processing](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/payment/paymentok.php#L1490-L1639)
4. The project-event capacity counter counts draft and validated registrations for the project. With the configured maximum reached, the public view displays a warning and withholds its ordinary form. A used-ticket count and an attendance count therefore need separate definitions. The back-office attendee list API checks event access and constrains project visibility and, when enabled, company scope. [Capacity counter](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/eventorganization/attendee_new.php#L119-L140) · [Form display](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/public/eventorganization/attendee_new.php#L810-L848) · [Attendee list](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/eventorganization/class/api_eventattendees.class.php#L213-L246)

## Acceptance cases

| Given | When | Expected observation |
| --- | --- | --- |
| Room A is booked busy 09:00–10:00 and the resource check is on | Add a busy 10:00–11:00 booking for Room A | The shared endpoint meets the conflict condition. A nonbusy association does not invoke that busy-booking check. |
| A staff member can create only their own agenda events | Submit an event owned by another identified user | The agenda API returns 403. |
| The operator marks a confirmed conference done | Read the agenda record after the update | Conference status is 4 and agenda completion is 100. |
| A public event has a registration fee of 115, with an illustrative rate of 15% | Register before paying | The attendee references a draft invoice. Its one service line has net 100, tax 15 and total 115. A registration submission has produced no bank receipt. |
| An unpaid registration already has a linked draft invoice with a fee line | Resubmit the same attendee email for the same event | The normal form reuses the registration/invoice and skips inserting a second fee line. |
| The callback successfully records the local collection in the billing currency | Read invoice payment, bank link if enabled, and attendee | Payment refers to the invoice, the attendee records the collected amount, and its validated status can be distinguished from a ticket already used for admission. |
