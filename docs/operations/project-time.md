# Project work, actual cost and time billing

A project groups tasks, people and commercial records. Tracking hours, valuing work and charging a customer are separate operations. An internal project can incur labour costs without a customer. Generating an invoice from time requires a customer on the project. The Projects module (400) is a release module. [Module descriptor](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/modules/modProjet.class.php#L50-L72) · [Operator guide](https://wiki.dolibarr.org/index.php/Module_Projects)

## Records and access

| Record | Fields and relationships used in this flow |
| --- | --- |
| Project | Entity and reference, title, optional parent project and third party, start/end dates, budget, public flag, status (draft 0, open 1, closed 2). Separate usage flags govern opportunities, tasks, time billing and events. |
| Task | Project, optional parent task, reference, start/end, planned seconds, effective seconds, progress percentage and billability. The reference is unique within an entity. Deleting a parent with subtasks is refused. |
| Time entry | Task identifier and element type `task`, worker, work date, optional start time, duration in seconds, optional service and note, recorded hourly rate. Invoice and invoice-line references trace subsequent billing. An intervention and its line have their own references. |
| Assignment | Project contact roles can reference internal users or external third-party contacts. Task assignments are a separate relationship. |
| Commercial records | A customer invoice can reference the project while many time entries reference one of its service lines. Supplier invoices, expense lines, stock movements and manufacturing orders can carry a project association for reporting. |

## Record time and reconstruct labour cost

1. On the time-entry screen, the user needs the time-recording permission (`projet.time`). Select a worker and task and supply a duration. A draft project is refused. A day-only entry retains that the start hour was unspecified. An explicit start time is preserved.
2. The REST operation `POST /tasks/{id}/addtimespent` instead checks project creation permission (`projet.creer`) and project resource access. It accepts date/time, duration in seconds, optional service, worker, note and progress. Omitting the worker selects the authenticated user. It returns a success envelope with code 200 and a message. A missing task yields 404, lack of access yields 403 and business-method failure yields 500.
3. If the configured back-entry window (`PROJECT_TIMESHEET_PREVENT_AFTER_MONTHS`) is exceeded, creation fails. On acceptance, the business operation writes the entry, invokes `TASK_TIMESPENT_CREATE`, recalculates effective task duration from all its time entries, updates task status from progress, and copies the **worker's** hourly rate into the entry. A failed trigger or failed task/rate update rolls back the transaction.
4. Summarize labour cost as the sum over entries of (duration seconds ÷ 3,600 × recorded hourly rate). A missing recorded rate contributes zero to this amount but increments the missing-rate count. An explicitly zero rate contributes zero with no missing-rate flag. The project overview includes a controlled recalculation action for stored rates. Historical reporting reads the entry rate.

**Task progress.** The business operation maps a supplied progress of 100 to closed, a nonzero intermediate value to ongoing and zero to validated. With no progress on the task object, it marks the task ongoing. The add-time REST wrapper only assigns a new progress when the supplied value is nonzero and within 0–100. An explicit zero in that wrapper cannot be used to reset an existing task's progress. ## Turn selected work into invoice lines

The work list offers eligible billable, uninvoiced rows. The invoice-generation action checks invoice creation permission and the presence of the project's third party. It opens a transaction and creates an invoice for that project/customer or fetches the invoice selected by the operator. It can copy the customer's payment method/account and apply the chosen terms, service and discount. The conversion creates service lines and writes invoice and line references back to time entries. Invoice validation, settlement and payment allocation belong to later finance operations. [Selection rules](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/projet/tasks/time.php#L2255-L2310) · [Generation and defaults](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/projet/tasks/time.php#L471-L545) · [Transaction result](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/projet/tasks/time.php#L854-L879)

| Grouping mode | Quantity and price | Backlink behavior in 24.0.3 |
| --- | --- | --- |
| Per time entry | One service line per selected entry. Divide hours by hours per unit of service and round the resulting quantity to two decimals. An entry-specific service can supply its own duration, price and taxes. | The update specifies the individual entry and worker. |
| Per worker | Group by worker and entry service, then divide combined hours by service duration and round to two decimals. The handler can use the worker's current rate, the weighted entry rates or the selected service price according to settings and service selection. | The writeback filters selected rows by worker only. When one worker has multiple service groups, later groups can replace the line reference on earlier entries. |
| Per task | Group by task and entry service. Use the configured quantity precision for hours ÷ service duration. With a selected service, use its selling price or, under `PROJECT_TIME_SPENT_INTO_INVOICE_USE_VALUE`, the weighted recorded hourly value × hours per service unit. The cost per invoiced service unit uses that weighted hourly value × service duration. | The handler retains the entry IDs per task/service group and updates only that group's entries. |

[Per-worker calculation and writeback](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/projet/tasks/time.php#L545-L647) · [Per-entry conversion](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/projet/tasks/time.php#L649-L755) · [Per-task conversion](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/projet/tasks/time.php#L758-L865)

**Worked job.** Two workers record 5,400 seconds at 40/hour and 1,800 seconds at 80/hour against a single task and service. The task totals 7,200 seconds and 100 of labour cost. Its time-weighted rate is 50/hour. If the service sells in two-hour units at 180, billing per task at the service price creates one unit at 180 before taxes and discount, with a calculated cost of 100 per unit. Switching the task-mode billing option to use recorded time value gives a sale price of 100 per unit. The normalized [time-entry schema](../../schemas/operations/time-entry.schema.json) describes one persisted task-time record, including the rate snapshot and optional billing trace. ## Read the project overview

Project profit is a configurable operational report. Its default contributions include customer invoices as income, and supplier invoices, project expense lines and qualified task time as costs. The overview lists manufacturing orders without including an MO header amount in the total. Stock movements enter the report only when the stock option and read permission allow them. Qualifying movements are valued at movement price × absolute quantity. Changing the configured lists of positive and negative item types changes the report. Replaced customer invoices are excluded, and the paid-invoice option filters for closed customer invoices. The displayed percentage, when shown, is 100 × tax-exclusive balance ÷ tax-exclusive revenue rounded to one decimal. ## Acceptance cases

| Given | Operation | Observable result |
| --- | --- | --- |
| A private project and an unassigned internal user with ordinary project read | Request project read | Denied. The same user can read a public project with that permission. |
| The worker's hourly rate changes from 40 to 80 after a one-hour entry | Record another hour for the same task | Effective duration is 7,200 seconds. Recorded cost totals 120 before any explicit rate recalculation. |
| One entry has a missing hourly rate and another has an explicit zero rate | Request the task cost summary | Their durations count. Both contribute zero value. Missing-rate count is one. |
| A third-party-free internal project has a billable task | Attempt to generate a customer invoice from its time | The action reports that a third party is required before creating the invoice. |
| Two billable entries for one user on different services | Convert both per task | Separate service lines receive the IDs of the entries that contributed to each group. Check the per-worker behavior above if rebuilding that mode. |
| Listed project invoice 180, project supplier invoice 20 and labour cost 100, all amounts excluding tax and no other qualified contributions | Read report as a user with the relevant rights | Balance is 60. The revenue-based margin is 33.3%. |
| The billing input contains a service with an invalid duration | Run the conversion | A negative duration lookup result records an error. The invoice conversion rolls back, including its new lines and backlinks. |
