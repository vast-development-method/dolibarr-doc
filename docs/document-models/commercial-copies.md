# Commercial documents and language selection

A sales office prepares a quotation in the operator's language, sends a translated offer with product sheets, then confirms the order in the customer's language and currency. The recipient, language, catalog text, quoted price and currency each have an independent source. Reproducing the transaction requires preserving the choices on the document as well as the company defaults.

## Choosing the language and recipient

1. The shared build action requires creation authority or document-generation authority. It reloads the record and its party and saves a submitted model. A selection represented by a numeric value yields a missing-model message.
2. The language starts as the operator's language. Under multilingual operation, an explicit output language takes precedence, followed by the linked party's default and then the record's own default if that record exposes one. With no selected value the operator language stays in effect.
3. A renderer can create a second translation context when the optional second language differs from the primary output language. Some titles and monetary captions then carry both translations. This option affects the labels the renderer chooses to translate. Each line still has a primary language for product descriptions and the attachment lookup.
4. The commercial header resolves recipient identity independently. A customer proposal and a customer order look up the first external contact in the customer role. When that contact belongs to another party, contact-company policy determines which name heads the block. The address builder receives the document party, the chosen contact and the contact-use flag. An enabled separate delivery-address section looks for the external shipping contact.

For example, an operator using English opens an order for a German-language customer. Printing a French copy with an explicit French language selects French for that operation. The source customer and its German default remain the same. Changing just the shipping contact may change the delivery address while keeping the same customer-account code and invoice party. Printing a second-language caption does not create another order.

Release evidence is in `htdocs/core/actions_builddoc.inc.php:64–109`, `htdocs/core/modules/propale/doc/pdf_cyan.modules.php:187–199,1858–1877,1957–1978,2008–2038` and `htdocs/core/modules/commande/doc/pdf_eratosthene.modules.php:1755–1777,1848–1872,1906–1930`.

## Product wording and supporting files

The common line-description routine distinguishes a catalog item from free text and uses the line's own label or description when present. With a catalog item and multilingual operation it loads the product translations. A translated catalog label or description can supply defaults when a line-specific value is missing. If the requested language differs from the operator's language, the routine also decides whether wording on the line still corresponds to the catalog text. An unmodified catalog label can switch to its translation. Replacing wording on the document can preserve the negotiated text. A separate option allows translation even when text has been modified.

The description comparison can account for markup and decoded entities. Where the stored description includes the original catalog wording, the routine can substitute the matching portion and preserve surrounding material. When only markup differs, it can use the translated description directly. A catalog description replaced with an entirely new customer instruction has a different result. A line-specific order instruction therefore needs its own stored value. Generating all product text anew from the current catalog would lose that distinction. Source is `htdocs/core/lib/pdf.lib.php:1905–2040`.

For the Cyan proposal, an optional product-document merge walks the proposal lines in order. It looks up supporting documents once per distinct product and includes the matches from the product's entity storage. With multilingual operation and a chosen language, the query restricts the product-file assignments to that language. It does not retry unqualified assignments when there is no match for the language. Without multilingual operation, this particular lookup has no language filter. Multiple files associated with the product can qualify. Repeating the same product on four commercial lines still performs one product-level merge selection.

For example, a pump appears twice, once as a unit sale and once in a commissioning option. Its German and English specification sheets have distinct language assignments. A German-language offer with product-file merge enabled selects the German assignment once. A French-language offer with no French assignment can still show its pump lines, but neither of those two files qualifies for the French merge query. This has no effect on the base quantity or the signed net price. See `htdocs/core/modules/propale/doc/pdf_cyan.modules.php:1006–1094` and `htdocs/product/class/propalmergepdfproduct.class.php:240–277`.

## Currency and financial identity

In the offer totals block, an active multicurrency module and a document exchange rate unequal to one select the stored document-currency net and gross fields. Otherwise the ordinary totals feed those amounts. When active, the additional operating-currency option can show another gross figure using the issuing company's currency. Some local-tax presentation branches convert an accumulated amount with the document's stored exchange rate and total precision. The renderer has no reason to obtain today's exchange quote merely because a user asks for a duplicate.

Suppose the stored net and gross amounts are 100 and 115 in company currency, and 80 and 92 in document currency, with a stored rate of 0.8. In the document-currency branch, the gross line of the summary represents 92. A second gross in company currency can show 115. At a rate of one, the tested branch reads the ordinary totals. Unit display, line discount, two-language captions and which columns appear operate independently. See `htdocs/core/modules/propale/doc/pdf_cyan.modules.php:1310–1396,1417–1433,1567–1591`.

An order pro forma invokes the regular order renderer with a pro forma heading. It retains the order as its source and can select the same order fields. Generating that output alone has no invoice validation, tax posting or payment allocation step. An operator can give a customer the pro forma for a deposit request and separately issue a deposit invoice that creates the actual invoice record. See `htdocs/core/modules/commande/doc/pdf_proforma.modules.php:42–77` and [Invoice print calculations and settlement evidence](../specification/output/invoice-print-calculations.md).
