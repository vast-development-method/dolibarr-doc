# OAuth connections, LDAP synchronisation and WebDAV files

Three different identities appear at these boundaries. An OAuth grant lets a configured service act within a provider's approved scope. An LDAP distinguished name addresses a directory entry. A WebDAV login identifies a user accessing a file collection. Preserve each identifier alongside the local account or entity to which it belongs.

## OAuth provider connection

| Stage | Contract | Observable result |
| --- | --- | --- |
| Configure | Administrator configures the service, provider parameters and intended redirect. Each provider has its callback. The generic connector supports separate configurations. | An application or user can start an authorisation request for the selected provider and scopes. |
| Start | Build the provider authorisation URI with the client ID, response type, requested scope and state. Store the corresponding state in the session. | Browser leaves the ERP for the provider's consent flow. An outstanding authorisation is distinct from a usable token. |
| Return | For the generic callback, when an expected session state exists, a mismatch refuses the code. A provider error or failed code exchange yields an error. | On a successful exchange, record the token and refresh token (when returned) with the provider and scope. The table can hold an expiry time, entity and optional user/party/member association. |
| Remove | Clear the token for the selected storage identity and service. | The local service can no longer use that stored grant. Provider-side revocation requires its own provider operation. |

The [grant metadata schema](../../schemas/integrations/grant-metadata.schema.json) is a portable read model for a **successfully stored authorisation**. It contains provider, entity, scopes and optional expiry or subject. Token values remain inside the credential store. Scope metadata is distinct from consent-round-trip state even though the storage table uses a field named `state` for scope in this path. [Administrative setup](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/admin/oauth.php) · [Consent exchange](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/modules/oauth/generic_oauthcallback.php#L191-L317) · [Scope persistence](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/modules/oauth/generic_oauthcallback.php#L326-L355) · [Storage fields](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/install/mysql/tables/llx_oauth_token.sql)

**Acceptance.** Start a grant, then complete the provider return with matching session state and an approved scope. Inspect the resulting metadata for that provider and owner. Complete another request with an existing, different expected state and confirm refusal before exchange. Clearing one locally stored grant must leave the other provider's connection usable.

## LDAP event projection

Directory sync has separate configuration for user/group, contact, member and member-type operations. For user creation in the outward direction, Dolibarr connects and binds, derives mapped attributes and the target distinguished name, then adds the LDAP entry. An update derives the old distinguished name from the previous object and the new name and attributes from the updated object. Renaming a login therefore requires retaining both identities until the remote change is complete. Group membership changes also carry old or new group context. The Active Directory enable/disable code path is limited to that server type. [Module guide](https://wiki.dolibarr.org/index.php/Module_LDAP_En) · [User add, update and membership](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/triggers/interface_50_modLdap_Ldapsynchro.class.php#L63-L187) · [User disable and group operations](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/triggers/interface_50_modLdap_Ldapsynchro.class.php#L223-L369)

Contact create/update/delete events use the contact mapping flag. Member operations additionally cover validation, subscription and termination under the member settings. A disabled module or explicitly suppressed synchronisation returns without work. A failing bind or directory write can return an error to the originating ERP trigger. The LDAP server and ERP database are separate systems. For a retry after an interrupted remote operation, verify the old and new distinguished names before applying a second change. [Contact events](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/triggers/interface_50_modLdap_Ldapsynchro.class.php#L370-L444) · [Member events](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/triggers/interface_50_modLdap_Ldapsynchro.class.php#L444-L545) · [Directory adapter](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/class/ldap.class.php)

**Acceptance.** Create a user with outward sync on, then update an attribute that changes its distinguished name. Confirm the existing directory identity moves to the new name using the earlier identity. Run a separate create with outward user sync disabled and confirm that event creates no remote user. These cases test remote directory behaviour independently of interactive login.

## WebDAV file collections

The file server builds its collection tree for an entity. It mounts the private directory, optionally exposes a public directory, and can mount the ECM directory when both ECM and its DAV setting are enabled. The private path names an entity collection. An authenticated request uses the user's Dolibarr login, rejects external party logins, and checks account status and validity dates. Optional IP restrictions apply at the endpoint. The enabled public path has separate access semantics. [WebDAV guide](https://wiki.dolibarr.org/index.php/Module_DAV) · [Scope and authentication](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/dav/fileserver.php#L65-L179) · [Mounted collections](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/dav/fileserver.php#L193-L207) · [Authentication and locking plugins](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/dav/fileserver.php#L224-L252)

**Service effects.** File operations work on the collection's filesystem contents. A lock database supports WebDAV LOCK and UNLOCK. A byte upload to a directory and a business command to validate an invoice have separate lifecycles. Acceptance cases include authenticating a valid internal user to the private route, refusing an external account there, testing that ECM appears only when both switches are active, and checking conflicting updates while a compatible client holds a lock. CardDAV and CalDAV collection registration are commented out in this file server and fall outside this contract.
