# Posting modes and completion

A posting request selects the order, quantities, warehouse and movement description. Identically named input and output arrays have different row-identity contracts on the partial and bulk services. The intended physical effect must be identified before interpreting the returned order ID.

| Operation | Source of a line's item and quantity | Where the actual points | How completion is determined |
| --- | --- | --- | --- |
| Workshop entry | The form iterates planned lines of the selected order. Each submitted nonzero warehouse or lot split supplies its own signed quantity. The all-remaining form proposes `max(0, plan − already posted)` on output rows. | Each `consumed` or `produced` actual points to the applicable plan row in `fk_mrp_production`. The movement identifier is nullable when there was no stock change. | When requested, compare the actual sum for each eligible **stockable** planned input and output with that line's quantity. Otherwise leave the order in progress. A separate manual close command can mark it produced. |
| Partial service | `arraytoconsume[].objectid` and `arraytoproduce[].objectid` identify **production-line rows**. Read the product and stock-change policy from each row. Direction comes from the array. One side may be empty. This service rejects tracked items. | One actual per processed entry links the passed plan line and, for physical changes, the new movement. A non-stock-changing line has no movement and no actual warehouse. | With automatic close, compare each saved planned input and output with its own linked signed actual total. With close disabled set in progress. |
| Bulk service using the saved plan | Used whenever both request arrays are **not simultaneously nonempty**. Walk all saved `toconsume` rows, then `toproduce` rows. Each nonzero quantity is the full planned quantity. A lone submitted array is not treated as a partial request. | Each actual links the plan row. A valid positive stored warehouse enables a physical movement. Tracked products cannot supply the necessary lot on this physical path. | With automatic close, sum by each existing plan-line ID. Equality or excess counts as fulfilled. |
| Bulk service with both arrays supplied | An entry's `objectid` identifies a **product**. Both arrays must be nonempty for this branch. A positive warehouse enables one issue or receipt at supplied price zero. | Each physical entry writes an additional planned-role row using the opposite direction (`toproduce` for input, `toconsume` for output) and also writes an actual of the requested direction. Both carry the same movement ID. Neither points to an original plan line. For a nonphysical entry only the actual is recorded. | Both completion flags start true and remain true when automatic closing is enabled. This branch does not reconcile earlier plan-line quantities. |

The two services require manufacturing write access, an order in validated or in-progress state, and nonempty `inventorylabel` and `inventorycode`. The submitted movement code groups movements. The write paths do not use it as a unique request key. On the workshop screen a failed posting rolls back the input and output splits together. The partial service begins a transaction, commits after the status update and reports failures as exceptions. The bulk service's outer operation has no transaction around all inputs, outputs and status changes. On an interrupted bulk operation inspect individual committed movements and actuals before deciding what remains to post.

## Reconciling incomplete production

The order plans ten components in and five finished units out. Two partial entries have already consumed four and produced two. The remaining quantities are six and three. The order is still in progress.

| Next action considered on that starting state | Consequence |
| --- | --- |
| Partial post of six inputs and three outputs against the corresponding plan IDs | Cumulative actuals reach ten and five. With close enabled the order becomes produced, assuming all other plan lines are satisfied. |
| Bulk post using the saved plan and valid warehouses | Posts ten more inputs and five more outputs. Cumulative actuals become fourteen and seven. Both plan comparisons pass despite the excess. |
| Bulk post with only an input array describing six | The bulk selector again takes the saved-plan branch. It does not limit its work to the supplied six inputs. |
| Bulk post with both product arrays, quantities six and three, positive warehouses and automatic close | The stock quantities move by six and three. New actuals have no links to the two original plans, whose linked totals remain four and two. The order can nevertheless become produced. |

One physical movement is the unit of stock reconciliation. In the last case the new input's additional planned-role row and its actual reference *one* movement. A report joining all `mrp_production` roles to `stock_mouvement` and summing the result would count this movement twice. Read each unique movement once, or begin with the stock journal and use the order-origin predicate. For a progress report restrict the roles to `consumed` and `produced` and retain whether each actual has a plan parent.

The stored flags answer different questions. `qty_frozen` determines scaling of a plan on a draft quantity change. `disable_stock_change` can permit operational progress without a movement. The catalogue's stockability determines which planned rows participate in the workshop's automatic completion check. Completing a service-only step can matter to a service-based reconciliation even when the workshop's stockable-row check can close the order without it.
