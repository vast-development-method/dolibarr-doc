# Audit evidence, diagnostics and extension changes

## Verify business events with BlockedLog

A signed journal entry identifies the business event, entity, time, source module or point-of-sale terminal, business reference, operator name and a serialized business snapshot. It can carry both tax-exclusive and inclusive values, method codes and linked references. Its signature binds the supported representation of the record to its predecessor. Stored format information matters when verifying an existing chain. The database record, its business snapshot and the module's chain state are distinct parts of the evidence.

The trigger selects specific business events, including customer and supplier invoice validation and the creation/deletion of customer, supplier and donation payments. For example, validating an invoice and later entering a customer receipt records two different business actions. Eligibility for invoice modification or deletion depends on the action and document state. The original financial document continues to own its state transition and amount.

For a control or export, follow the chain in order and recompute each recorded signature against the previous signature. The control can detect a mismatch and reports the record affected. A range or exported month also needs boundary checks against its next record or the chain-head evidence when it ends at the latest record. An authorized read/export user selects a year and optionally a month. The archive is persisted under the configured output location and has its own verification data. A passing check establishes consistency of the checked evidence within these controls. It does not establish the commercial correctness of the original amounts.

**Rebuild acceptance.** On a disposable installation, validate a sales invoice and record a receipt. Export the relevant period with the authorized auditor role, verify the archive and record the result against its date range. A second, read-only verification of the same unchanged period must confirm the same event sequence. For a restore drill, restore matching database, configuration and document-store snapshots into an isolated instance and run the same verification there. Preserve the original archive and result as independent comparison material. This drill is a proposed acceptance procedure.

## Diagnose requests with system logs and DebugBar

System logging checks module activation and a maximum severity threshold, then dispatches eligible messages to configured handlers. Numeric severity grows less urgent from emergency towards debug. A chosen handler restriction can limit delivery. The included handlers target an application file and the operating system log. DebugBar collects request context, page timing, memory use and queries. It has a separate use permission (`debugbar.read`), and the administrator can control its log source and line count. Technical messages, timings and queries support troubleshooting; signed business events above support audit verification.

**Acceptance.** With a warning-level threshold and the file handler on, an error is eligible for delivery and a debug-level message is filtered. A request with the debug permission can feed its page log buffer; a signed journal check reads the journal independently of that buffer.

## Change an extension or an extra field

| Operation | What changes | Boundary to verify |
| --- | --- | --- |
| Generate a module object | The builder requires module activation and the run right. It copies templates and generates object properties, views, module definitions and table definitions. A property can describe type, nullability, default, indexing, relationships, presentation and validation. | The generator owns marked source sections. A regeneration can change material in those sections. Capture the generated change set and review the descriptor, object class and DDL together. |
| Package and enable | The builder has a package generation action. The template descriptor loads the module's SQL, then initializes the module registrations. | File generation, extension deployment and SQL execution happen at different times. Record the package version and the schema state actually deployed. |
| Disable the generated module | The template remove method delegates to the common removal routine with its supplied removal statements. | A disabled feature is no evidence that custom table schemas or pre-migration field values have been restored. Inspect the module's actual removal and migration definitions. |
| Add an extra field | An input definition captures type, visibility, editability, permissions, default, uniqueness and personal-data classification. A data-bearing field maps to a column on the object's extra-field table. Section separators only need a display definition. | Check both the metadata and the physical schema. The data policy worker reads the personal-data flag when anonymizing an object. |
| Delete an extra field | The operation removes its definition in scope. Before dropping a physical column, it checks whether the same field is still defined in another entity. | One entity may lose the field in the UI while the shared column still exists. Removing its last definition can drop the column and the stored values. |

**Reproducible change test.** In an isolated copy, retain the original extension package and a matching database/document snapshot. Generate one new business field, apply the new package and open both an existing record and a new record through the normal UI or API. Confirm that old records still load, a valid new value round-trips, and the correct entity can see it. Restore the original code and data snapshot into another isolated copy and rerun those same reads. For a dynamically defined extra field, repeat with two entities that declare the same name. Removing one definition should retain the shared column. This procedure tests the extension change and the recovery path without assuming a reversible generator or a transactional filesystem.
