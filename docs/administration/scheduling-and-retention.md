# Scheduled execution and retention policies

A job definition contains the owning entity and module, handler type, schedule, activation condition and optional execution window. The same row also tracks attempts, last start and completion, result, output, processing flag and process ID. A scheduler invokes the runner periodically. Enabling a descriptor installs its schedule definition. Execution still requires a runner invocation and the configured conditions. ## Selection, execution and retry

| Step | Rule | Evidence visible to an operator |
| --- | --- | --- |
| Select | The ordinary URL runner takes enabled, nonprocessing jobs in ascending priority, entity, then record ID. The activation condition must hold. Next-run must be empty or strictly earlier than now. Start/end boundaries are inclusive. | An active job with next run exactly equal to the poll time qualifies on a later poll. |
| Enter the job | Resolve the configured login, set a positive job entity as the execution environment, record the attempt start, clear prior completion and result, mark processing, set PID and increment run count. | Failure to resolve the login prevents execution. Run count measures starts. |
| Execute | A method job returns zero or boolean true on success. False or a nonzero numeric result means failure. Command jobs require the separate command-execution setting. | Completion writes result/output, finish timestamp, clears processing and PID. An optional configured email address receives failure alerts. |
| Advance schedule | The runner attempts reprogramming after a completed success **or failure**. Positive repeat intervals advance the previous scheduled time until it reaches or exceeds now. Whole days/weeks advance on the server's local calendar; month schedules use calendar months. | Missed periods advance the schedule without automatically replaying each missed business event. Archive mode can retire a job when its attempt limit or schedule end is reached. |
| Recover an interrupted run | The job registers shutdown cleanup for an unfinished attempt. The URL runner also checks old unfinished attempts against a configured age (24 hours by default), and can detect a missing process where the host supports that check. | Clearing an interrupted attempt allows future execution. Verify the business records touched by the handler before replaying an externally visible action. |

**Example.** At 12:07 an eligible hourly job is still scheduled for 10:00. One invocation runs it, then advances its schedule to 13:00. A failure at 12:07 is visible in the result before the next scheduled attempt. The scheduler's processing flag describes the attempt. It cannot acknowledge a message delivered to an outside service. A rebuild can use a stable business operation ID and reconcile that service's acknowledgement on retry. This is an implementation choice for external delivery.

The [attempt schema](../../schemas/administration/job-attempt.schema.json) captures a running or finished attempt as a normalized snapshot. A finished nonzero outcome is a recorded failure. The timestamps, count and status belong to the scheduler. The application's output can describe a separate business error. ## Retain, anonymize or delete records

The Data Policy descriptor registers a daily method job, initially enabled and conditional on the module. An administrator sets policy delays. A nonpositive or unset delay disables the corresponding action. Each policy uses its own eligibility query with the active entity and a delay in months. For example, the recruitment candidature deletion policy looks for both an old application modification date and the absence of a recently modified agenda action for that candidature. [Job registration](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/core/modules/modDataPolicy.class.php#L164-L168) · [Administrator setup](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/datapolicy/admin/setup.php#L89-L127) · [Policy definitions](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/datapolicy/class/datapolicycron.class.php#L64-L268)

The release implements anonymization rules for customer, prospect, mixed-role and supplier third parties and associated contacts. It also defines member anonymization when Membership is active, optional deletion for eligible third parties with neither customer nor prospect status under that policy's conditions, and candidate deletion with Recruitment active. Field selection belongs to the policy. The member policy changes identifying and contact fields and assigns the resigned status. Nonempty custom values declared personal are scrubbed by field type: text receives a replacement marker, numeric values are reset, date-like values receive the policy's sentinel date, and multiple-choice values are cleared. This is software behavior; choosing retention delays remains a separate organisational decision. [Member and recruitment policies](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/datapolicy/class/datapolicycron.class.php#L227-L269) · [Anonymization and personal extra fields](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/datapolicy/class/datapolicycron.class.php#L425-L513)

For each policy, the worker tries deletion first, then anonymization. Deletion checks whether a supported object with child records is in use and skips the delete if so. Anonymization can retain the business key and relationships. The worker tracks processed numeric row IDs across the run. Two object types with the same numeric ID can consequently collide in that tracking list. An implementation requiring one action per distinct business record should key its own tracking by type and ID and specify this behavioral difference. The job runs the database changes in one transaction, returns zero with anonymized/deleted counts on success or one with error details after rollback. [Execution and transaction](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/datapolicy/class/datapolicycron.class.php#L283-L331) · [Per-policy selection and used-record guard](https://github.com/Dolibarr/dolibarr/blob/5c6c7ff6a5112413b1c27221c8d11750afad56f8/htdocs/datapolicy/class/datapolicycron.class.php#L347-L400)

## Acceptance cases

| Input and action | Expected result |
| --- | --- |
| Disabled job, false module condition, or start time later than the current poll | No attempt starts. |
| Eligible method returns a nonzero result | The runner records a failure and proceeds to reschedule. |
| Retention delay is zero for an action | The action skips selection. Other configured actions remain eligible. |
| A deletable third party still has a linked document and independently qualifies for anonymization | Deletion skips the in-use record. Anonymization can update the identifying fields while preserving the document link. |
| A supported personal custom numeric value and an ordinary custom numeric value are populated | Anonymization resets the personal value. The ordinary field falls outside the personal-field query. |
| A later policy records an error after an earlier policy changed rows | The policy worker rolls back the database transaction and reports failure. Successful persistence must be verified by re-reading the records after completion. |
