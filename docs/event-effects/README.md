# Which subscribers run when a record changes?

A customer invoice can send mail, mark a linked order billed and deliver data outside the ERP while its own validation transaction is still open. To reconstruct the outcome, start with the event code, the order in which subscribers saw the object and the connection or service that owns each write. The [business event catalogue](../events/README.md) identifies individual transitions. [Setting interactions](setting-interactions.md) works through specific decisions, and [delivery and replay](delivery-and-replay.md) follows their failure paths.

## Dispatch contract

The dispatcher needs an object and a valid configuration. Invalid inputs return an error before subscriber selection. An invalid language object is replaced with a fresh translator and an invalid actor with a fresh user object. The latter supplies no identity from the initiating request. One configured precondition is checked before dispatching `BILL_VALIDATE`. With `MAIN_FRANCE_TODO_LOI_FINANCE` enabled, validation of a sales invoice is refused when the issuer is in France and subject to VAT, the loaded counterparty is an individual, and the immutable log is disabled.

Subscribers registered for all modules are eligible on every dispatch. The others require their named module to be enabled. The dispatcher discovers built-in and registered extension subscribers and sorts by priority, then module token and subscriber name using natural ordering. Each receives the event, the **same in-memory business object**, actor, language and effective settings. A later subscriber can see fields an earlier subscriber changed or cleared. A business operation invoked by a subscriber can dispatch another event before the outer loop resumes.

A positive dispatcher result counts **subscribers reporting success**. A zero counts none. If any return negative, the dispatcher returns minus the number that failed, gathers their error messages and records the last failing subscriber. The magnitude of an individual return has no weight. An unbalanced transaction depth when a subscriber returns is counted as one failure. The dispatcher does not restore that depth. A negative return allows later subscribers to run, while an exception escaping a subscriber interrupts the loop immediately. The originating operation decides whether to roll back its own unit of work.

## Names constructed at dispatch time

| Operation | Event construction | What the receiver sees |
| --- | --- | --- |
| Generic record create, update, delete | Uppercase runtime class followed by `_CREATE`, `_MODIFY` or `_DELETE` | The record on which the shared operation ran. Suppressing triggers skips these calls. Specialised domain methods can use an entirely different prefix. |
| Generic line removal | `LINE` + uppercase parent runtime class + `_DELETE` | The parent object. Where configured, ownership is checked first. This shared method dispatches inside its transaction **before** deleting the line, including when the method receives its suppression argument. A negative result prevents the delete. |
| Contact and resource association | Contact changes use the object's trigger prefix or uppercase element plus `_ADD_CONTACT` or `_DELETE_CONTACT`. Resource changes uppercase the configured trigger prefix and append `_ADD_RESOURCE` or `_DELETE_RESOURCE`. | The object receiving or losing the association. A generic link between two business records instead emits `OBJECT_LINK_INSERT`, `OBJECT_LINK_MODIFY` or `OBJECT_LINK_DELETE`. |
| Shared status update | Uses the code the caller supplied when triggers are enabled | The database update has succeeded on the current connection. The object receives an old copy, and its new in-memory status is assigned only after dispatch succeeds. The handler can therefore see the previous status in the object. |
| Public or private note change | Uses an element-specific mapping or the trigger prefix/uppercase element plus `_MODIFY` | The in-memory note has been set. Party, customer invoice, supplier invoice and expense use their business prefixes. A recurring invoice note actually emits `BILLREC_MODIFIY`, including that spelling. Matching requires the emitted code. |

The [subscriber setting register](subscriber-settings.csv) gives the stored keys and the stage where each value is read. Extension-defined subscribers enter the same ordering rules. Their effects depend on the installed extension.

## Finding subscribers for one event

The [event-to-subscriber register](event-selection.csv) lists dedicated event branches and supported notification codes by exact spelling, followed by the applicable subscriber and priority on each row. Pattern rows describe configurable or generic selection. For `BILL_VALIDATE`, for example, the commercial workflow has a dedicated branch, the calendar has a dedicated activity description, notifications accept the code, and the immutable log can record it. Targets configured for that code can additionally receive a webhook. For `STOCKTRANSFER_VALIDATE`, the notification subscriber accepts the code, with calendar fallback and webhooks subject to their independent configuration.

A dedicated calendar branch supplies activity data for a particular event and often requires the matching object type. Other eligible events use generic activity data. A notification row establishes eligibility for recipient resolution. A dedicated immutable-log row establishes a branch that checks the event, while actual logging also requires a qualified object and a tracked or controlled event. Security-log rows are the codes with defined audit labels.

## Concrete codes from shared record operations

The [constructed event register](constructed-codes.csv) follows 212 distinct routes from named record operations to generic creation, update, deletion or line removal. It resolves 176 distinct codes across 57 record types, including manufacturing orders and lines, accounting templates, staff evaluations, stock counts, transfers and workstations. Sixteen of these codes also appear in the [371-code event catalogue](../events/README.md), giving 531 distinct names across the two registers. The entries describe reachable method branches with their suppression rules. A successful call still depends on the record data, module, owning operation and subscriber results.

For example, a bill-of-materials clone can emit the same creation code as a new bill of materials. Generic header creation normally inserts its supplied child lines with their own triggers suppressed before emitting the header event. A workstation's separate creation of user-group and resource associations omits suppression. Removing a consumed production line goes through the parent manufacturing order and can emit `LINEMO_DELETE`. The asset depreciation-options upsert explicitly suppresses generic creation in the path that inserts new options. Caller-supplied status codes, dynamically configured extension names and indirect calls through arbitrary runtime objects remain subject to the dispatch rules above.
