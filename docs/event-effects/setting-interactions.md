# When several event policies apply

## Customer invoices and supplier bills

Assume a customer order for 1,000 before tax, one validated invoice for 600 and a second invoice for 400 now being validated. The following results count calls to classify the order in an isolated execution of the commercial subscriber. An order's own transition determines whether an attempted classification changes its stored state.

| Enabled policies on invoice validation | Other linked invoices | Classification requests |
| --- | --- | ---: |
| Current invoice amount equals eligible linked orders | Validated 600 | 0 |
| Current invoice comparison and cumulative invoice comparison | Validated 600 | 1 |
| Both comparisons | Validated 600 and a further draft for zero | 0 |
| Both comparisons and permission to classify unequal amounts | Validated 600 and a further draft for zero | 1 |

The single-invoice rule compares the rounded pre-tax invoice amount with the sum of validated, in-shipment and closed linked orders. The cumulative rule requires exactly one source order, accepts the currently validating invoice explicitly, and requires every other linked invoice to be validated or closed. It rounds the invoice sum and the order amount at total precision and compares them. Enabling the unequal-amount setting changes only branches that call the shared comparison. The two rules run independently within the same subscriber. They can both request classification when both comparisons pass.

The same event can classify signed or already billed proposals, close validated shipments under the shipment-close rule, or mark validated/closed shipments billed. The shipment modes compare rounded linked shipment totals with the invoice. The unequal-amount setting does not enter either comparison. Changing the order to billed can itself emit a nested event and classify the linked proposal before invoice processing reaches its own proposal branch. `BILL_PAYED` has a separate order-classification switch. Settlement and validation have different entry conditions. [Commercial automation](../events/commercial-automation.md)

On `BILL_SUPPLIER_VALIDATE`, the purchase order condition accepts a qualifying match in base currency **or** a match in document currency if all eligible orders share the bill's currency code and the bill's foreign pre-tax total is nonzero. For eligible orders of 110 in base currency and 100 in the bill's currency, a bill for 111 base and 100 foreign can classify the order. A different currency code removes that second route. The unequal-amount policy applies to both calls to the shared comparison. The supplier quote branch uses signed or closed quotes and their base pre-tax amounts. The receipt-billed branch sums validated/closed receipt totals and directly compares with the bill's base pre-tax total, without the shared override or explicit total-precision rounding. Each branch requires its own module, setting and linked records.

## Warehouse movement and order completion

A shipment-validation or closure event can trigger a change of sales order status. The receipt pair does the same for a supplier order. Both require a recognised order origin and a positive origin ID. The subscriber builds two maps keyed by product ID. One adds quantities on positive-status dispatches or receipts linked to the order. The other adds ordered quantities, omitting non-stock services when service stock is disabled and always omitting title/separator lines of type 9. Every **ordered** key and quantity must match in the fulfilled map. Excess quantity on an ordered key fails equality. An extra key appearing only on the fulfilment side does not fail this one-way comparison. Repeated product lines are combined, even if they came from separate order lines.

Consider an order for six units of a part and one service. With service stock off, receipt of the six parts can satisfy order completion. With service stock on, omitting the service leaves the comparison incomplete. A site can classify a purchase order fully received on receipt validation while the warehouse increases only on receipt closure. For a sales order, closure can immediately start automatic invoice creation, including a bank account fallback when the order lacks an account, the party supplies one, and order entry did not request a bank choice. The dated warehouse ledger, order status and linked invoice therefore require three separate checks. [Stock posting decisions](../policies/stock-posting-decisions.md)

## Ticket contract, intervention, mail and contacts

Contract lookup runs at priority 20. It needs the workflow, ticket and contract capabilities, a configured service category, the contract-link setting and a ticket party. The optional parent-company search starts with the ticket's own party and moves up its hierarchy. The first company with eligible contracts wins. Draft or validated contracts qualify if they include a category-matching service in initial or open state. The query groups matches by contract and specifies no order. For each returned contract the subscriber calls the ticket setter. Only one `ticket.fk_contract` value fits. If contracts 8 and 13 are returned in that order, two successful updates leave 13 on the ticket. A failed setter is ignored. Multiple matches can produce a warning.

The setter updates the stored ticket without changing the event object's `fk_contract`. With intervention creation enabled, the same subscriber copies the in-memory contract, project, party and actor onto the new intervention, sets its document model, reads configured extra fields from the request, and records the ticket as origin. If the ticket originally had no contract, a stored link to 13 and an intervention with no contract are possible together. A failed intervention creation sets a user-facing error without producing a negative return. Repeating ticket creation's event can create another intervention. In an isolated execution the search skipped the empty party, reached two contracts on its first matching ancestor and left the next ancestor unexamined. A ticket with an original contract ID of 4 finished with stored ID 13 and an intervention carrying 4. With the second write made to fail, the ticket retained 8 and the subscriber still returned zero.

Ticket mail runs at priority 50. Party defaults run at 90 and webhooks at 95. A default contact first attached at 90 cannot be a recipient chosen from ticket links earlier during that event. A later subscriber that needs the newly stored contract must reload it. A serialised event object can still contain the original value.

| Ticket mail branch | Recipient decision |
| --- | --- |
| Administrator at creation or closure | A configured administrator address and an empty `disableticketemail` event context allow this branch. |
| Assignee | A populated assignee distinct from the actor, a successful user lookup, an address and enabled assignee mail allow sending. The create path also checks the suppression context. Optional ticket-specific suppression of the sitewide automatic copy applies during composition. |
| Customer at creation | The request's `notify_tiers_at_create` flag and an empty suppression context are required. Prefer the selected active contact with an address, otherwise use the party's address if a party is present, otherwise the origin email. |
| Customer at assignment | An assigned user, an enabled customer-assignment notification and an empty previous assignee qualify. Starts with the origin address and adds distinct linked customer-contact addresses. |
| Customer at closure | With an empty suppression context, an explicitly selected contact must be linked and external. The all-contacts choice or confirmed bulk closure can gather all linked addresses. With no linked contacts, the closure-notification switch can supply the party's address to that list. |
| Tracking and template | Customer messages include a tracking link when the public ticket interface is enabled. The configured public base and ticket tracking identity determine the URL. The selected template is looked up by label and type. |

## Employees, memberships and manufacturing

A leave type's `block_if_negative` rule checks the employee's balance and working-day count before the approval transaction opens. A rejected request never reaches `HOLIDAY_APPROVE` here. An accepted request that emits the event can generate an activity and a subscription notification independently. The monthly-debit policy controls when entitlement is reduced. A mail receipt establishes neither the working days deducted nor the balance available for a later request. [Workforce settings](../settings/projects-and-workforce.md)

A subscription notification can target an active contact subscribed for that party, an active subscribed user, or a configured fixed recipient. For a fixed address with a configured minimum, a nonempty pre-tax amount at or below the threshold suppresses the notification. Zero or an absent total skips that comparison. Thus a threshold can filter valued documents differently from a leave request. The subscription choices govern expense validation and approval, and stock-transfer creation, modification, validation, return to draft and closure as separate event codes.

On `USER_MODIFY`, an outbound directory mapping can update a user, then use `newgroupid` or `oldgroupid` from the event context to refresh group membership. User login logging, directory writes and optional calendar history are independently gated. On `MEMBER_SUBSCRIPTION`, outbound member synchronisation additionally needs at least one mapped first/last subscription amount or date or last expiry field. Member validation and termination update directory status only with the status mapping enabled. A linked mailing-list subscriber can still act without those directory field mappings.

Creating, editing and deleting a bill of materials through the shared record methods emits `BOM_CREATE`, `BOM_MODIFY` and `BOM_DELETE`. Workstations use `WORKSTATION_CREATE`, `WORKSTATION_MODIFY` and `WORKSTATION_DELETE` on the equivalent paths. Workstation creation can also invoke shared creation on its group and resource associations. A configured webhook can match a constructed event code. The automatic activity rule additionally checks its per-code switch. The default notification sender restricts itself to its own supported list. A subscribed observer of a workstation edit receives a change to the routing resource, while manufacturing consumption or output requires its own posting operation.
