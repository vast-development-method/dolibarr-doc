# Settlement messages and trade declarations

A checkout return, a provider payout and a trade declaration each identify a different transaction. A checkout links customer money to an invoice. A payout moves an amount between internal bank accounts. A declaration selects transactions for a reporting period. These paths have different matching keys and different evidence of completion.

## From a payment notification to a local entry

The inbound notification handler selects its test or live service, requires a configured executing user and verifies the event signature before dispatch. A positive result from an installed event handler ends standard dispatch with HTTP 200. In connected multi-company mode the account mapping can change the active company. Reading the event type alone therefore cannot identify the records that changed.

| Event or entry point | Match and decision | Local effect |
| --- | --- | --- |
| Successful interactive checkout | Given a nonempty transaction ID, the return handler searches both `paiement.ext_payment_id` and `payment_donation.ext_payment_id` for the exact ID or that ID followed by a colon and a suffix. A match or a failed lookup stops another recording. This check has no service or entity predicate. | The selected invoice flow can create a receipt, populate `paiement_facture`, close a settled invoice and create a bank entry when enabled. A subsequent return finds the recorded transaction. |
| `payment_intent.succeeded` for an invoice direct debit | First resolves `prelevement_demande` by exact `ext_payment_id` and `ext_payment_site`. With no matching request the normal handler acknowledges and stops. For a generated debit it expects `type = ban` and `traite = 1`, then checks the provider payment method. | The debit branch checks for an existing `paiement` by either long or short external ID and matching service. It can create an absent receipt/allocation. With banking enabled it independently checks for a recorded payment with a nonzero `fk_bank` before posting a bank entry. An eligible transferred debit batch can advance to credited, record the actor and credit date, and set its lines to status 2. |
| `payout.created` with automatic payout recording enabled | Uses the provider arrival time and the active entity to store the service's next scheduled payout. | Attempts a notification after saving the schedule. This branch creates zero bank movements. Failure to save the schedule returns a server error. |
| `payout.paid` with automatic payout recording enabled | Clears the schedule before beginning the transfer. Fetches the configured payment-clearing and receiving bank accounts. Compares their IDs and converts the provider amount using the configured company currency. | Equal account IDs skip both legs. Different IDs receive a negative `PRE` and a positive `VIR`, with the same payout ID in `bank.num_chq`. Two reciprocal `bank_url` rows of type `banktransfert` point to the opposite movement. The posting date is the local processing date. |

The transfer transaction contains both bank movements and both relationships. Failure in a leg or relationship rolls back this unit. The already-cleared schedule stays cleared. After this inner rollback the handler still returns 1 and skips the completion mail. A successful pair triggers a mail attempt whose result does not control the posting. Compare the payout reference, each account's signed total, and both relationship endpoints before using an acknowledgment to reconcile a bank balance. A financial institution's statement is separate evidence of the receiving account's actual credit. [Payment and bank workflows](../treasury/online-payments.md)

### What happens when the same event arrives twice

| Case | Arrangement | Observed result |
| --- | --- | --- |
| Checkout guard, sequential | Record an external transaction in the long form. Run the short-ID lookup again. | The existing receipt matches. An earlier donation receipt can also satisfy the union. |
| Checkout guard, overlapping | Two database sessions both complete the lookup before either receipt header is visible. Each inserts a header with the same external ID. | Both inserts committed under read committed and repeatable read. The next lookup found two rows. The receipt header has no unique key for the provider ID. The allocation key on `(fk_paiement,fk_facture)` applies to a specific receipt ID. This exercise covered the guard and declared receipt schema. Other posting steps can still stop either checkout. |
| Payout, sequential | Two deliveries report the same payout of 40 between different accounts. | The executed event branch created two pairs and four links. The native schema also accepted both pairs. Clearing totals −80, receiving bank totals +80, and the combined transfer total remains zero. |
| Payout, overlapping | One database session posts a pair under the same payout number while the other pair is still uncommitted. Each uses its own generated movement IDs. | Both pairs and four links committed. The unique link key `(fk_bank,url_id,type)` accepts the new pairs because their movement IDs differ. |
| Payout, posting failure | Force relationship creation to fail after both legs are inserted. | On the executed handler branch, the bank transaction rolled back, the schedule remained cleared and the return value was 1. With identical configured account IDs the handler also returned 1 and inserted zero movements. |

The payout control-flow cases used the event branch with controlled bank and mail adapters. The two-session cases used the declared transactional database tables and keys. These exercises concern local receipt and transfer recording. Provider acceptance, downstream bank settlement and recipient receipt each have their own evidence. ## From invoices to a trade declaration

The reporting feature defines a record, two XML builders and a file-download operation. The register stores `ref`, `entity`, `type_declaration`, `periods`, `mode`, `content_xml` and `type_export`. The builders are callable separately. The standard record card and list contain no call binding those builders or the download method to a filing action. The download operation writes the supplied XML to a temporary file named from the runtime `period` property and streams it to the caller. The declared record uses `periods`. The helper that asks for the next number queries `MAX(numero_declaration)` filtered on `exporttype`. Neither column is in the declared table. A caller can supply its own numbering context. A saved reference alone establishes no assigned authority number. [Storage definitions](../relational-model/fields.csv)

| Output | Source and filters | Values written |
| --- | --- | --- |
| Goods arriving | `facture_fourn_det.fk_facture_fourn → facture_fourn.rowid`. Goods departing use `facturedet.fk_facture → facture.rowid`. Both branches join an existing catalogued product and third party, and left-join the invoice companion by `fk_object`. | Builds an envelope and declaration with six-character minimum left-padded number, reference period, currency, function and direction. Arrival is `A` and dispatch is `D`. |
| Goods item | Positive document status, line `product_type = 0`, current entity, invoice date within the inclusive month, and foreign or missing party country. A missing country on a selected party records an error and rejects the goods output. | `CN8Code` comes from the item customs code. `MSConsDestCode` comes from the party country. `netMass = round(weight × qty)`. The code reads stored weight directly. `quantityInSU` is the line quantity. `invoicedAmount = round(invoice.total_ht)` for each selected line. Both region and origin codes use the first two party postal-code characters. `modeOfTransportCode` reads `mode_transport` from the invoice companion. |
| Freight category | When configured, goods in the freight category are deferred until ordinary rows have been processed. The builder looks up the highest non-freight product-line net on the invoice and fetches a customs code using that amount. | The freight row retains its quantity, weight and invoice amount and uses the customs code returned by that lookup. The lookup has no ordering to select between equal-highest amounts. |
| Services dispatched | Uses sales invoice lines with `product_type = 1`, the same document and entity filters, and the same foreign-or-null country selector. The SQL still selects the transport column. | Each `ligne_des` contains its sequence, rounded **invoice header net**, and the party VAT number. The goods-specific missing-country check occurs only on the goods branch. |

A controlled invoice of 150 net had two qualifying goods lines and one service line. Weights 2.25 and 1 with quantities 2 and 1 produced masses 5 and 1. Each goods line carried 150, and the service line also carried 150. Summing the goods XML amounts yields 300 for one invoice of 150. The builder queries did not split the invoice total across source lines.

Three conditions produce different outcomes in the same builder. A successful query returning no rows gives an error and no XML. A selected goods party lacking a country also gives an error and no XML. Removing the required physical `mode_transport` column made the query fail. The item builder then fell through to success and returned XML with zero items and no item error. These cases executed the XML builders against a controlled invoice database. Inspect query success, selected line count, document totals and the serialized item count independently.

The record, generated bytes and download belong to the ERP. A submission identifier, a rejection reason or an accepted filing requires a response from the receiving authority. The record schema has no filing receipt or acknowledgment field and the download path makes no transmission to the authority. Declaration and payment registers have their own period rules.
