# A customer invoice from printable copy to sent attachment

An invoice has a financial identity, a current printable file and, when sent, correspondence history. Each answers a different question. The invoice establishes the receivable. Its PDF shows what the renderer produced using the selected language and current records. The sent event records a submission. To establish the exact bytes delivered earlier, there must also be a separately retained copy of that transmission or its attachment.

## From invoice to current file

| Step | Decision and persistent effect |
| --- | --- |
| Open the invoice | The invoice and customer must be within the acting user's document scope. The invoice card uses invoice-read authority to display generation controls, and invoice-create authority for the normal manual build action and file-removal control. A separately granted generation capability can satisfy the common build action where supplied. |
| Choose layout | The explicit selection takes priority. Without it, the invoice uses its saved `model_pdf`, then the configured model for the invoice's type, then the general invoice default, then the standard PDF model. Manual selection saves the named model on the invoice before the renderer runs. A failed attempt can therefore leave the newly selected model on the record. |
| Choose language | The manual build starts in the operator's language. When multilingual operation is enabled, an explicit document language wins. Otherwise it uses the customer's default language when available, then an applicable object default, then the operator's language. These choices affect rendering. The request does not change the customer's preferred language or mint another invoice number. |
| Write the standard PDF | For a real invoice the fixed-layout renderer chooses the output root for the invoice entity, falling back to the working entity when the invoice has no entity value. Beneath it, the directory and PDF basename use the sanitized invoice reference. For reference `INV-42` the file is `INV-42/INV-42.pdf`. Each regeneration uses that same name regardless of output language. |
| Add standard terms, if selected | An enabled terms-of-sale option opens the configured terms PDF in the invoice document storage, imports readable pages and appends them in order. Those pages become part of the invoice PDF. A page that fails import can generate a warning. This is separate from a second attachment chosen in the email form. |
| Record the file | After successful rendering, the generation workflow removes stale previews. If the returned filename exists it updates the index. The standard fixed-layout renderer also requests that the invoice's `last_main_doc` be set to the relative file location. A custom generator can return another name or decline to update this pointer. |

The [invoice print calculations](../specification/output/invoice-print-calculations.md) describe the distinction between gross, receipts and printed balance. [Commercial copies](../document-models/commercial-copies.md) describes translated product and recipient wording.

## Index identity, share and failures

The location key on `ecm_files` is `(filepath, filename, entity)`. Generation looks up the relative location in the working entity and stamps new index entries with that entity. In the ordinary path the operator is working in the invoice's entity. The PDF writer's physical-root decision uses the invoice's entity. These are separate decisions when reconciling records shared across companies. For a particular invoice, match the entity and location as well as `src_object_type` and `src_object_id`. A printable reference by itself is insufficient.

At a new location the index records the relative directory and filename, the generated-file marker and source invoice. Its `label` holds the current content fingerprint. At an existing location the same row is updated with the latest fingerprint and source, generated origin, empty original path, description and keywords. The old digest is not kept in a revision field. When public invoice download is enabled a missing share value can be issued. Existing share values survive a regeneration at the same indexed location. Someone using the same public link can consequently receive a different language or rendering later. Authenticated access uses module and document access checks. A public share resolves the indexed file and its entity independently. [Document access and revocation](../specification/information/document-index-and-sharing.md)

There are three different failure outcomes.

1. A failure before the writer reaches its output call does not demonstrate a new PDF. The model choice may already have changed. Check the existing file and its index before treating the attempt as a successful revision.
2. The writer emits the bytes before running its post-generation extension. If that extension reports failure, the standard writer returns an error and the common success path skips index and main-pointer refresh. A replacement PDF can already exist while the stored digest still describes the previous bytes.
3. The common success path calls the index writer but does not use its return to determine the overall build result. Failure to create or update the index can leave a readable file and a warning or stale metadata. A later failure to set `last_main_doc` can leave both the bytes and the index in place. Successful rendering alone does not establish all three writes.

If `MAIN_DOC_CREATE_METAFILE` is enabled, the generation workflow can also overwrite a sidecar containing invoice reference and date, customer, line count, net/gross and line facts. It is a current summary of the document. It contains neither the previous PDF nor a complete byte-for-byte representation.

## From current file to submitted message

1. The composer first uses a readable regular file at `last_main_doc`. Otherwise it searches the invoice's document directory for the most recent matching reference. If no readable candidate exists it attempts generation in the selected output language and searches again. It does not regenerate a readable candidate simply because the message language changed.
2. The invoice card offers sending under the invoice-read grant in ordinary mode or the dedicated invoice-send grant in advanced mode. It passes the candidate file to the message template. If the template selects attachments, the composer registers the path, outgoing filename and media type. The operator can change the attachment list before sending. The draft tracks these paths in the session under the invoice tracking identity. The same outgoing filename is added only once. Registering a path does not freeze its bytes.
3. On submission, the operation resolves the primary recipient, optional copies and final message. The transport receives the selected paths, names and types. Choosing a template, adding an attachment, removing one or cancelling does not submit mail. An English message can enclose a German PDF if that PDF was chosen.
4. Transport acceptance precedes the transaction that increments the invoice's sent counter and emits `BILL_SENTBYMAIL`. The event may carry message ID, sender, recipients, subject, body, attachment descriptors and the invoice link. A transport refusal does not enter that success transaction. A downstream error after acceptance can roll back the counter and event although the recipient may receive the message. Re-submitting can send another copy.
5. With automatic event recording and attachment retention enabled, the event handler checks each attachment name in the source object's document directory. If the destination does not already exist, it attempts to move the attachment there with the source reference and event ID. An existing destination is left alone. Sending the ordinary main PDF, which already occupies that destination, therefore does not create a separately named historical copy through this option.

## Two revisions in two languages

Assume one invoice with three units at 50, no discount and 20% tax. It has net 150, tax 30 and gross 180. The customer prefers German. Both dates of rendering occur before any receipts or financial adjustments. “First” and “second” below identify the copies in the example, independently of any database revision number.

| Action | Current file and index | What remains available |
| --- | --- | --- |
| Build the first copy in English and submit it with an English message | The standard PDF has English headings, gross 180 and fingerprint A. The index points to invoice 42 and the invoice points back to the location. | The recipient receives the English attachment on successful delivery. A configured sent event may also exist. |
| Explicitly regenerate in German | The same filename now contains the German copy with gross 180 and fingerprint B. The same index row is refreshed. | The invoice, amounts and reference remain the same. The standard main-file path now serves the German rendering. |
| Open another English message draft and leave the current attachment selected | The composer finds the readable German PDF and uses its path. | The chosen email language changes the text or template. It does not restore the English PDF. |
| Preserve both renderings under a selected archive policy | Retain the first PDF under a distinct protected location or distinct authorized attachment name before overwriting it. Record invoice ID, entity, language, content fingerprint, recipient and transmission identity with the retained copy. | This is an additional retention policy. The normal same-name build and optional sent event alone do not maintain both versions. |
| Remove the current main PDF from the invoice card | Physical deletion is attempted first. After a successful unlink, the file operation tries to remove its index entry in the invoice entity. An index-deletion error can warn after the bytes are gone. This action contains no reset of `last_main_doc`. | The invoice and its financial records remain. A later composer checks the pointer for readability, then searches or rebuilds. The recipient's earlier attachment and any independently archived copy are outside this removal. |

An indexed share can be revoked while the file remains. Deleting only an index record is a different operation from removing the file on the invoice card. For exact transmission history, reconcile the sent event and the separately retained artifact using their invoice and message identities.
