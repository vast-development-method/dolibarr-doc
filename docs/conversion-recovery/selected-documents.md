# Selected documents, failure boundaries and repeat entry

Each of the four billing registers starts one transaction around its selection. It creates draft headers and lines first, then optionally issues the target invoices. Grouping is an in-memory map keyed by party. After a new invocation the map starts empty. A successful nested draft creation can therefore be rolled back by a later source or validation failure in the same invocation. The issue loop runs only if the conversion's error counter is zero.

| Stage | Customer orders | Shipments | Supplier orders | Receipts |
| --- | --- | --- | --- | --- |
| Source admission | A nonpositive fetch skips the source. A fetched draft, cancelled or already billed order produces a warning and is skipped. Other eligible orders proceed. | A nonpositive fetch skips the shipment. No corresponding draft or billed-state test in the conversion loop. | A nonpositive fetch skips the purchase order. The conversion loop does not exclude previously billed orders. | Source IDs are sorted. A missing or draft receipt increments the shared error counter. Even an earlier eligible group is subject to rollback. |
| Header and origin | First party header or new per-source header. Nonpositive creation and zero return from the main link writer count as errors. Copying extra shipment links under the optional policy checks the link results. | Header creation and primary shipment link are checked. Copying the selected additional origin links checks their return too. | Creation is checked. The order-to-payable link is a direct insert. A failed insert increments the error counter. | Creation and main receipt link are checked. On the first grouped receipt, successive supplier order IDs are assigned into one association slot before creation, so the last one survives there. Reuse of a header can add supplier-order associations from a later receipt, and that additional link's return is ignored. |
| Detail rows | A nonpositive ordinary line result counts as an error. The optional follow-up storing extra line parameters has no return check here. | The ordinary copied line must return positively. Quantity derives from the shipped allocation. | Ordinary payable lines check the returned ID. The order ID passed for the supplier line origin is distinct from the source detail's own row ID. | The receipt attempts a link from the newly created payable detail to the receipt before testing the detail writer's result. A failed detail creation counts as an error. The link writer's own return is ignored, so a successfully created line can lack its allocation link. |
| Negative-price rows and notes | Where conversion into an absolute discount is enabled, discount creation failure counts. The subsequent attachment result is assigned without an error increment. The optional public-note update return is ignored. | The negative-price discount's creation result is checked. Its subsequent attachment return is not tested in this branch. | Discount creation is checked. The attachment return is assigned without an error increment. The public-note update and classification of the source order as billed have no checked return here. | Discount creation is checked. Its attachment return is assigned without an error increment. A receipt/source currency mismatch appends an explanation without incrementing the shared error counter. |

A positive previous result permits the outer commit path despite a negative validation result. A stale nonpositive result can instead initiate rollback. | The actual issue result is checked. A nonpositive value stops issuance and selects rollback. |

A checked failure on one line stops that source's detail loop. The surrounding selection may still fetch other records and perform more work before reaching its final decision. Consequently, notifications and bookkeeping messages do not establish the order in which durable records become visible. For ordinary errors where all nested calls leave the transaction depth balanced, the outer rollback discards every candidate written through that connection.

## The two failure points in supplier issue

The supplier validator first reloads the party and lines. It can return before opening its own transaction, for example when the supplier reference begins with the configured copy prefix or no lines exist. If the order-based caller tests a positive earlier line result, the target can remain a draft in a committed selection and the source order may already be marked billed.

After passing admission, the validator opens a nested transaction and updates `facture_fourn.ref`, `fk_statut`, `fk_user_valid` and `date_valid`. Depending on stock policy it next records movements, then dispatches `BILL_SUPPLIER_VALIDATE`. A negative subscriber result triggers a nested rollback and a negative return. The database wrapper implements nested calls with a depth counter. At depth above one, rollback decrements the counter without issuing a database rollback or restoring a savepoint. If the order-based caller ignores that negative return and really commits at depth one, the earlier status and reference update can survive. The in-memory invoice may still carry the draft state. Read the header in a fresh transaction, and independently reconcile downstream effects.

There is a third outcome if stock-on-supplier-invoice is enabled. A negative movement result causes the validator to return immediately with `-2` before it closes its own nesting level. If the movement writer has returned with its own level balanced, the outer order-billing commit or receipt-billing rollback only decrements the depth from two to one. Neither statement has finalised the database transaction. Same-session reads can still see the writes. A fresh reader does not see them, and a physical rollback removes them. Connection cleanup and any later outer operation determine the eventual outcome.

## Generation and side effects

Customer order, shipment and receipt billing call the document builder after successful validation and before the selection's final commit. A failed generation sets an error message and clears the current action. The builder does not increment the billing loop's shared error counter on that branch. The issue loop sets the build action once before iterating. If the first render fails and clears that action, a later invoice can still issue while its build section is skipped. Conversely, a file produced for the first invoice can survive a later invoice's rollback. The supplier-order issue loop does not invoke this explicit build step.

Check the rendered document and message history separately. If an enabled subscriber has already sent externally, the SQL rollback cannot recall delivery.
