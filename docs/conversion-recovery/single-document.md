# Single-source conversions and after-creation failure

In a service conversion, source access is checked before creating the target. A later error in the response does not identify which earlier work has committed. Determine whether the call runs directly or as a subscriber to a larger transaction.

| Conversion | Order of writes and decisions | Outcome to check on retry |
| --- | --- | --- |
| Order → customer invoice | Check source read, invoice creation, source scope and order eligibility. Copy eligible line data, header fields, configurable values and links, then call the normal invoice creator. On a positive creation result the converter calls the after-conversion hook. A negative hook result returns conversion failure. | The direct service has no encompassing transaction around the creator and this hook. An otherwise eligible source can already have a new draft even when the service reports 405. Inspect source links and quantities before attempting another invoice. |
| Contract → customer invoice | Check contract read, target create and resource scope. The converter can accept a list of contract detail IDs. The direct service passes the contract without a narrowed list. Draft creation precedes the same after-conversion hook. | On a direct late failure, inspect the existing invoice and which services and periods it contains. Using the same contract again can copy services already on the earlier invoice. |
| Quotation → sales order | Check source read, target create and source scope. The conversion creates the target and its origin links, then calls the order after-conversion hook. The independent service propagates a negative converter result as 405. | An order can persist even though the hook failed. With automatic order validation enabled, the converter attempts validation only after a successful hook. It returns the created order ID even when that validation fails. Read the actual order state when a valid order was requested. |
| Accepted quotation or closed order → automatic downstream document | The signing/closing operation starts its own transaction. If enabled, the subscriber calls the appropriate converter. A negative converter return is passed to the source operation. The order-close subscriber can also try to assign the customer's bank to a new invoice and return an error from that step. | A failure propagated to the owning source transaction can roll back the source transition and target writes together. A caller handling the independent service after a committed creation has a different outcome. Compare the source state as well as its links. |
| Order or quotation → deposit invoice | The deposit routine checks eligible origin type, date, payment terms, configured deposit schedule and requested percentage. Once admitted it starts a transaction, creates the deposit, builds tax-category lines and optionally adjusts the first line for gross rounding. It executes the after-conversion hook and optional validation before the outer commit. | A nonpositive header creation, negative line write, negative adjustment, negative hook or negative optional validation selects rollback and returns no deposit. The line and optional validation checks specifically test negative results. On a top-level call with balanced nesting, failure discards the deposit and links. A higher-level enclosing transaction must act on any returned failure. |

For a conversion that produces a draft and later reports a failure, read the existing header and lines before deciding whether the missing work is draft creation, automatic validation, a downstream subscriber or output. Retrying only a missing operation is possible when the relevant record still exists and the normal state, privilege and settlement rules admit it. If a subscriber performed an externally visible action before failing, reconcile its own delivery record too.
