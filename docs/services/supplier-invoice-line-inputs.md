# Supplier invoice line inputs and pricing

A buyer can add a draft supplier invoice line with `POST {id}/lines` or amend a known line with `PUT {id}/lines/{lineid}`. Both operations check supplier-invoice write permission and access to the parent invoice. Amendment also loads the line and verifies its parent before calculating amounts. The parent comes from the route. The body supplies the purchase price, tax and quantity. A recurring invoice supplies these values from a template through a separate creation path.

The [request schema](../../schemas/services/supplier-invoice-line-request.schema.json) represents the route, identifiers and recognized input properties. The [create](../../examples/services/supplier-invoice-line-request--create.json) and [change](../../examples/services/supplier-invoice-line-request--change.json) examples use the actual body field names. A client sends only the `body` as its request payload.

## Field contract

Neither nested handler applies the invoice-header validator or fills a request from the stored line. They sanitize the description as restricted rich text and sanitize the supplier reference. Properties below describe the ordinary baseline without extensions.

| Input | Create | Change |
| --- | --- | --- |
| `description`, `ref_supplier` | Line text and supplier’s item reference. The writer trims the description. Configured supplier-price lookup can replace the reference. | Replaces the description. The persistence method uses the submitted supplier reference, falling back to the line’s generic reference when empty. To preserve a supplier reference, send it. |
| `qty`, `pu_ht`, `remise_percent` | Quantity, unit input before discount and line discount percentage. Empty quantity and discount become zero. A predefined price can fill an empty unit input and zero discount for a catalogue item. | Quantity, unit price and discount are recalculated from the body. Omitting a value does not ask the handler to reload its old amount. A description-only change can rewrite financial amounts as zero. |
| `price_base_type` | Defaults to `HT`, price excluding tax. `TTC` means the input includes VAT, before supplementary local taxes, even though the input field is named `pu_ht`. | Same default and interpretation. The stored net unit price is calculated from that basis. |
| `tva_tx`, `localtax1_tx`, `localtax2_tx` | Empty rates become zero. VAT can include its source code in parentheses, for example `20(VAT20)`. The calculation resolves local-tax rules from the rate and parties. Insert stores the applicable local rate when the resulting local tax is nonzero. | Same coded VAT input. The writer sets the local-rate fields from the supplied rates and persists the calculated local tax totals and types. A standalone `vat_src_code` property is outside the nested mapping. |
| `fk_product`, `product_type` | A positive product ID must exist. An empty ID creates a free line. The stored type comes from the input, ordinarily 0 for product and 1 for service. A negative type fails. | A positive catalogue ID fetches the item and supplies its type for storage. Missing or zero ID retains the stored product ID, while the supplied type is used in that branch. Sending zero alone cannot detach the catalogue item. |
| `info_bits`, `fk_unit` | Tax and line flags default to zero. Empty unit becomes null. | Rewritten from body. An empty unit can remove the old unit. |
| `date_start`, `date_end` | Optional service period. An absent date stores null. When both are supplied, start later than end fails. | Same ordering check. Supply both stored bounds to preserve an existing service period. The nested handler passes the values to the date writer without a separate date-string parsing step. |
| `rang` | Omitted or null becomes −1. A negative rank appends at current maximum rank plus one. Explicit zero is stored as zero. A positive occupied rank can shift existing lines down. | The writer includes rank in the update only when the supplied value is nonempty. Omitted, null or zero preserves the stored rank. A supplied nonzero rank writes directly. The update does not run the insertion-time rank-shift loop. |
| `array_options` | Nonempty per-line custom field values go to the extension-field writer after creation of the base row. | The writer first fetches existing extension fields and overlays only supplied keys. Other keys survive. |
| `multicurrency_subprice` | With multicurrency enabled, a positive foreign unit price clears the base input before calculation. The invoice’s exchange rate is used to derive the base amount. | Supplies the foreign unit directly alongside the base input. This path does not clear a nonzero base input when a positive foreign unit is also supplied. |
| `fk_code_ventilation`, `special_code`, `origin_id` | Allocation code and special code default to zero. Origin ID is forwarded on the in-memory line to the insert/event path. The base detail insert has no origin-ID column. | These three properties are outside the amendment mapping. |
| Parent-line ID, absolute-credit ID, total fields and trigger switch | The nested service leaves parent line and absolute-credit linkage at their business-method defaults. Totals are computed. The service passes zero for trigger suppression. | The nested mapping likewise exposes no command to change a parent-line or absolute-credit association or to suppress events. |

This distinction matters on update. A caller that loads an invoice from the read service sees display labels, calculated totals and catalogue metadata. A change request must supply the writable financial values it wants to retain. The line’s custom-field merge and the rank rule are specific exceptions to ordinary replacement.

## Three prices with different origins

**Direct input.** An ordinary catalogue line can use the submitted unit amount without selecting a supplier-price record. For two units at 50 excluding tax, a 10% discount and 20% VAT produce 90 net, 18 VAT and 108 gross, assuming ordinary recoverable VAT and no local tax. Changing the quantity to three while resending the same price, rate and discount gives 135 net, 27 VAT and 162 gross. The header reprices from its lines following either operation.

**Supplier price tiers.** When `SUPPLIER_INVOICE_WITH_PREDEFINED_PRICES_ONLY` is 1, adding a catalogue item requires a qualifying price for the supplier and product. The nested service passes no particular supplier-price row. Its lookup ignores the supplied supplier reference when matching and, for a positive line quantity, selects the highest tier quantity that does not exceed it. A qualifying record with pack total 180 for 10 units yields a unit price of 18. A supported dynamic price expression can supply the pack total. A nonzero submitted unit price stays in effect, while the reference comes from the matched record. A submitted discount of zero is replaced by the tier’s nonzero discount. A missing eligible tier aborts creation even if the request contains a price. Amendment does not call this tier lookup.

**Recurring template.** The generator reads the lines in template rank order. It passes each template line’s stored tax-exclusive unit price, VAT and source code, local rates, quantity, product, discount, rank, supplier reference, optional unit, custom fields and special code into the normal add-line operation. Template period fields are flags. When set, start becomes the generated invoice date and end becomes the day before the next scheduled date, where that date exists. The generated call passes zero for the foreign unit price. Its inherited currency calculation can therefore derive a foreign amount from the base price and the invoice rate.

The recurring branch separately looks for a missing internal buying cost. It considers configured product cost, weighted average cost when applicable, and the best supplier price. That computed local buying-cost value is absent from the subsequent add-line argument list. For a template with unit price 19, a current internal cost of 12 does not change the generated unit to 12. If predefined supplier prices are enforced, the generation still runs the ordinary eligibility check and can fill a zero template unit or discount from the qualifying supplier tier.

On credit notes the stored quantity is the absolute quantity. The normal sign rule forces the unit and base net, VAT and gross totals negative. Keeping originating discount-line signs requires both the negative-lines option and the keep-origin-discount-lines option. Creation also applies its sign rule to local tax and foreign totals. The update path separately writes calculated local and foreign totals and uses its sign rule on the base net, VAT and gross fields.

See [recurring invoice generation](../specification/financial/recurring-invoice-generation.md).

## Events, totals and return values

| Operation | Event and durable result |
| --- | --- |
| Create | The domain method explicitly gates insertion on a draft header. A nondraft parent returns zero, which the handler passes through. A successful insertion returns the **new line ID**. The line obtains its ID, writes extension fields and emits `LINEBILL_SUPPLIER_CREATE`. The parent then recomputes totals, updates ranks where needed and commits the surrounding transaction. A negative insert result maps to 400. |
| Change | The handler checks line ownership, and the business method repeats that check. It captures the previous line and custom fields, writes revised data, saves custom fields, and emits `LINEBILL_SUPPLIER_MODIFY` within the line writer’s transaction. That transaction commits before the separate header repricing call. A nonpositive result maps to 304 and may represent a business error. A repricing failure can therefore follow a durable line change. |
| Change response | After successful repricing the handler calls the ordinary invoice read operation and returns the updated invoice. This last step requires supplier-invoice read permission and performs the parent access check again. A read failure at this point does not reverse the completed mutation. |
| Generate from template | Generated lines emit the normal line-create event. After header total calculation and header custom fields, the generator emits `BILL_SUPPLIER_CREATE` before committing the outer invoice creation. Line subscribers can see the new line before finalized header totals. A reported line or header event error can roll back this creation. |
| Remove | The nested delete operation checks both IDs, then releases any linked absolute discount, invokes the line-delete path, recalculates the header and commits. `LINEBILL_SUPPLIER_DELETE` fires before removal of the stored line and extension values. A failure reported by the deletion path maps to 405. |

Parent access or write-grant rejection returns 403. Missing invoices or missing target lines return 404 through their respective lookup paths. A mismatched line and invoice return 403. A fresh create request has no request-level idempotency key. After an interrupted response, reading the invoice and its lines can distinguish an already-created line from an unsuccessful attempt before a second insertion.

The nested routes do not interpret a body `caller` field as synchronization context. The separate invoice-header creation service does. An enabled webhook with a matching event can observe the line event before the enclosing invoice operation finishes. A blocking target failure can veto the operation in the transaction that emitted the event. A successful remote delivery survives any subsequent database rollback. The [finance event catalogue](../events/finance.md) identifies the exact emission sites.
