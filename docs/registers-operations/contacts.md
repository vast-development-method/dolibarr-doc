# Contacts

The base row is `socpeople` in an allowed contact entity. The party, country, department, region, prospect-contact status and optional additional fields are left joined. An unlinked person therefore remains eligible for the ordinary list. The screen checks contact access and the `societe.contact.lire` grant. An external user's party ID replaces the requested party. Where the user's party context supplies an ID, the final query requires that linked party. Privacy is evaluated on the contact row.

| Input | Predicate |
| --- | --- |
| `search_priv`, `userid`, `search_status` | Default privacy admits public contacts and private contacts created by the viewer. Zero selects public only. One selects the viewer's private contacts. `userid` separately filters the creator. Status defaults to active (1), with a nonnegative selected status compared to `statut`. |
| `socid`, `type`, `search_sale` | Positive party context requires the joined party ID. Type `o` means no linked party, `f` supplier, `c` customer (party `client` 1 or 3), `p` prospect (2 or 3). A positive sales representative requires a matching party assignment, −2 means no sales representative. The parsed `search_type` is separate from the active `type` discriminator. |
| `search_categ`, `search_categ_thirdparty`, `search_categ_supplier`, `search_roles` | Test the contact category, linked party customer category and linked party supplier category against their own link tables. Each category path handles one selected ID or −2 for no link. Roles use an existence test on `societe_contacts` for this person and any selected role ID. |
| `search_level`, `search_stcomm` | Match prospect-level codes as a string list, and contact prospect-status IDs as an integer list. Empty or −2 prospect status leaves that test off. |
| `search_id`, `search_ref_ext`, `search_firstname`, `search_lastname`, `search_firstlast_only`, `search_poste` | Positive ID uses numeric comparison. The rest are keyword searches on external reference, first name, surname, either name, or job title. |
| `search_societe`, `search_societe_alias` | With the alias column hidden, a supplied company name searches legal name and alias together. With the alias column displayed the two fields can be matched separately. |
| `search_phone`, `search_cti`, `search_phone_pro`, `search_phone_perso`, `search_phone_mobile`, `search_fax` | General phone searches across work, personal and mobile. CTI strips non-digits and then leading zeroes from the input before searching those columns. Individual controls restrict to one number or fax. |
| `search_email`, `search_no_email`, `search_<network>` | Keyword match address. With mailing enabled, positive no-email requires at least one opt-out for that exact address. Zero requires a nonblank address with no opt-out. When social networking is enabled, an active network's filter tests its stored network-specific value. |
| `search_address`, `search_zip`, `search_town`, `search_state`, `search_region`, `search_country` | Keyword match on address, postal code, town, department name and region name. Country uses the selected ID list. |
| `search_note_public`, `search_note_private`, `search_import_key`, `search_all` | The dedicated controls address the corresponding stored field. Global search uses the configured searchable contact fields plus party name/alias when enabled. It omits private notes from its external-user global field set. |
| `search_date_creation`, `search_date_modif`, `search_birthday` start/end inputs | Inclusive start-of-day and end-of-day comparisons on `datec`, `tms` and the full stored `birthday`. A birthday range compares calendar dates including year. |

A public active warehouse contact and a colleague's private active contact share the same customer and telephone extension. A phone search by a different user admits only the public contact. If that person also has a supplier-contact role, the role lookup still returns one person because it tests for a link rather than joining every role as a result row.
